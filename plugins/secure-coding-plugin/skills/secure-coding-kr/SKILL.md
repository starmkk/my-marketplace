# 소프트웨어 보안약점 진단가이드(2021) 허브 스킬

> 근거 문서: 행정안전부·한국인터넷진흥원(KISA), 「소프트웨어 보안약점 진단가이드」, 2021년 11월 개정판, 총 612페이지.
> 이 스킬의 모든 페이지 표기 `(p.N)`은 위 원문 기준이다. **원문에 없는 내용은 "문서 미기재"로 명시한다.**

## 1. 개요

- 「행정기관 및 공공기관 정보시스템 구축·운영 지침」(행정안전부고시 제2021-3호)에 따라 정보시스템 구축·운영 시 SW 보안약점이 없도록 안전한 소프트웨어를 개발하기 위한 가이드다 (p.12).
- 대상 독자는 **전자정부 SW 보안약점 진단원**이며, 발주자(보안 요구사항 도출)·사업자(개발보안 적용 개발)·감리법인(보안설계 확인·보안약점 진단)도 활용한다 (p.12).
- 진단 범위: 신규 개발 또는 유지보수로 변경되는 소프트웨어의 **설계 및 구현단계 보안약점 진단** (p.12). 감리대상 정보시스템 사업이 적용 대상이며, 감리대상 외 사업도 자체 적용한다 (p.17, 전자정부법 시행령 제71조).
- **기준 항목 수 (확정)**:
  - **분석·설계단계 보안설계 기준: 총 20개** — 입력데이터 검증 및 표현 10 / 보안기능 8 / 에러처리 1 / 세션통제 1 (p.17, p.38)
  - **구현단계 보안약점 제거 기준: 총 49개** — 입력데이터 검증 및 표현 17 / 보안기능 16 / 시간 및 상태 2 / 에러처리 3 / 코드오류 5 / 캡슐화 4 / API 오용 2 (p.17, p.39)
  - ⚠️ 업계에서 널리 쓰이는 **"47개"는 2019년 이전 판 기준**이다. 2021 개정판은 **49개**이므로 혼동하지 말 것.

**이 스킬을 쓰는 상황 3가지**:
1. 진단 **기준 자체**(설계 20개 / 구현 49개 항목, CWE 매핑, 페이지 근거)를 확인·인용할 때.
2. 분석·설계단계 또는 구현단계 **진단 절차**(착수→진단→보고→종료, 1차→제거→2차→종료)를 수행·안내할 때.
3. 정적분석 결과의 **오탐(False Positive) 판별** 근거가 필요할 때.

## 2. 어떤 스킬로 갈 것인가 (라우터)

이 스킬은 secure-coding-plugin의 **허브**다. 작업 성격에 따라 아래 표대로 분기하라.

| 상황 / 요청 | 이동할 스킬 |
|---|---|
| **Java / JSP / Android 소스코드**의 구현단계 보안약점 진단, 시큐어코딩 구현·수정 | `secure-coding-java` |
| **C / C++ 소스코드**의 진단·수정 (메모리 버퍼 오버플로우, 포맷 스트링, 해제된 자원 사용 등) | `secure-coding-c` |
| **모바일 전자정부 앱**의 KISA 소스코드 검증 신청·대응 (보안명세서, 보완조치내역서, FV- 항목) | `mobile-app-verify` |
| 사용된 **암호 알고리즘·키 길이·유효기간**의 국내 권고 적합성 판정 | `crypto-policy-kr` |
| **모바일 앱**의 OWASP 국제표준(MASVS/MASTG/MASWE) 기준 보강 점검 — KISA 제출·제도 판정이면 `mobile-app-verify`, 국내 기준 공백의 국제표준 보강이면 여기 (**제도 판정 근거 아님**) | `owasp-masvs` |
| **웹·API**의 OWASP 국제 검증 요구사항(ASVS) 기준 점검 (**제도 판정 근거 아님**) | `owasp-asvs` |
| 진단 **기준 자체**·**진단 절차**·**설계단계 보안설계**·**오탐 판별 근거**·제도(고시·역할) 질의 | **이 스킬 (secure-coding-kr)** |

분기 예시:

| 사용자 발화 예 | 분기 |
|---|---|
| "이 Spring 컨트롤러에 SQL 삽입 있는지 봐줘" | `secure-coding-java` (판정 근거·오탐 규칙은 이 스킬 인용) |
| "C 코드에서 strcpy 썼는데 취약한 API 지적 대상이야?" | `secure-coding-c` + 이 스킬 **49번 「취약한 API 사용」(CWE-676 등)** 근거. 외부 입력이 실제로 버퍼 한계를 넘을 수 있으면 **16번 「메모리 버퍼 오버플로우」(CWE-119)에도 이중 해당** 가능 |
| "KISA에 앱 검증 신청하려면 뭘 내야 해?" | `mobile-app-verify` |
| "SHA-1을 HMAC으로 쓰면 괜찮아?" | `crypto-policy-kr` |
| "설계단계 보안설계 기준이 몇 개고 뭐가 있지?" | **이 스킬** (5절 + `references/design-phase-20.md`) |
| "도구가 Null 역참조라는데 이거 오탐 같은데?" | **이 스킬** (8절 오탐 판별 표) |
| "앱에 인증서 피닝이 없는데 지적 대상이야?" | `owasp-masvs` — 원문 미기재 영역이라 국내 기준으로는 지적 불가. 지적 시 OWASP 컨트롤 ID 와 **"구속력 없음"** 병기 |
| "루팅 탐지를 안 넣었는데 검증 부적합이야?" | `owasp-masvs` §2 ↔ `mobile-app-verify` FV-5 — **방향 반대 항목**. 탐지 미구현은 국내 기준 위반이 아니다 |

- 실제 코드 진단은 언어별 스킬(`secure-coding-java`/`secure-coding-c`)로 넘기되, **기준 번호·CWE·오탐 판정 근거는 이 스킬의 references/를 인용**한다.
- OWASP 계열 스킬(`owasp-masvs`, `owasp-asvs`)은 국내 기준의 **공백 보완재**다 — 구속력 없는 기술 권고이며 **부적합 판정 근거로 쓰지 않는다**. 지적 시 컨트롤·약점 ID 와 "구속력 없음"을 병기한다.
- 암호 관련 약점(21, 22, 23, 24, 25, 28, 31번)에서 알고리즘·키 길이의 적합/부적합 판정이 필요하면 반드시 `crypto-policy-kr`을 함께 참조한다.
- 한 코드가 두 기준에 **이중 해당**하는 경우(예: 무검증 `strcpy` → 16번·49번)의 주(主)/부(副) 선택 규칙은 원문 미기재 — 보고서에 **양쪽 근거(항목명·CWE·페이지)를 병기**할 것을 권장한다.

### 3.3 SW 보안약점 진단원 (p.21)

- 기존 역할: **구현단계 소스코드**의 보안약점을 진단하고 조치방안을 제시.
- 개정 지침에서 추가된 역할: **분석·설계단계 산출물의 보안설계 항목 식별** 및 **보안 대책 수립 여부 진단**.

| 구분 | 내용 |
|---|---|
| 교육 대상 | SW 개발경력 6년 이상 또는 취약점 진단 3년 이상 |
| 교육 절차 | 진단원 양성과정 교육 신청 → 경력증명 서류 제출 → 교육 수료 |
| 교육 시간 | 5일 40시간 |
| 교육 내용 | SW보안약점 이론 학습 및 진단 실습 |
| 신청 방법 | 사이버보안인재센터 홈페이지 (https://academy.kisa.or.kr/main.kisa) |

## 4. 진단 절차

### 4.1 분석·설계단계 진단절차 (p.21~27)

진단 시점: "설계가 완료되고 구현이 시작되거나 구현을 준비하는 시점" (p.20). 진단 대상: 분석·설계 과정의 설계 산출물 (p.20).

```
[착수] ─→ [진단] ─────────────────────────────→ [보고서 작성·제출] ─→ [종료]
착수회의     산출물 접수 → 산출물 검토              초안 작성 → 공동리뷰      종료회의
(진단원·     → 보안약점 진단·개선방안 도출          → 보고서 제출            (결과 설명,
 발주자·     → 공동리뷰 → 개선방안 확정                                      개선 확인)
 사업자)
```

| 단계 | 주체 | 입력 | 산출물 / 내용 |
|---|---|---|---|
| 착수회의 | 진단원 (발주자·사업자 참석) | — | 진단 목적·적용기준·진단항목·일정 설명, 산출물 요청 (p.22) |
| 산출물 접수 | 개발사 → 진단원 | 분석·설계 산출물 | 제출 목록 확인, 누락·추가자료 요청 (p.22) |
| 산출물 검토 | 진단원 | 산출물, 보안설계 기준 20개 | 보안설계 항목 식별, 보안 대책 수립 여부 확인 (p.22~23) |
| 진단·개선방안 도출 | 진단원 | 검토 결과 | 기준 충족 여부, 객관적 근거(가이드·법률) 기반의 실행 가능한 개선방안 (p.23) |
| 공동리뷰 | 진단원·발주사·개발사 | 진단현황 | 주요 문제점 설명, 의견 청취, 실행 가능성 확인 (p.23) |
| 개선방안 확정 | 진단원 | 공동리뷰 결과 | 설계항목별 일관성, 증적 자료 기반 확정 (p.23) |
| 보고서 초안 → 제출 | 진단원 | 확정 개선방안 | **최종진단결과보고서**: 진단 결과·진단원·기간·대상 범위·개선방안 명시 (p.23~24) |
| 종료회의 | 진단원 | 최종 보고서 | 결과 설명·질의응답, 개선사항 기한 설정·완료 확인 (p.24) |

진단대상 산출물 (p.24~26):

| 단계 | 산출물 |
|---|---|
| 분석단계 (표2-4) | 요구사항 정의서, 요구사항 추적표, 유즈케이스 명세서, 유즈케이스 다이어그램 |

### 4.2 구현단계 진단절차 (p.28)

```
[1차 진단] ─→ [보안약점 제거 수행] ─→ [2차 진단] ─→ [종료]
CC인증 도구      개발자가 관련               수정 소스 재진단,     1·2차 결과 및
+ 수동진단 병행   소스코드 개선               제거 여부 확인        제거 여부 요약 보고
```

| 단계 | 주체 | 입력 | 산출물 / 내용 |
|---|---|---|---|
| 1차 진단 | 진단원 | 작성 완료된 소스코드 | **1차 진단보고서** — 필수: 검출 파일명, 라인번호, 보안약점명, 원인설명, 대응방법 (p.28) |
| 보안약점 제거 | 개발자 | 1차 진단보고서 | 보안약점 관련 소스코드 개선 (p.28) |
| 2차 진단 | 진단원 | 수정된 소스코드 | **2차 진단보고서** — 1차 검출 보안약점의 **제거 여부** 추가 (p.28) |
| 종료 | 진단원 | 1·2차 결과 | 결과·제거 여부 요약 보고 (p.28) |

- 진단은 **CC인증을 받은 SW 보안약점 진단도구**를 활용하되, **미탐 최소화를 위해 수동진단을 병행**한다 (p.28).
- 대부분 소스코드 작성 완료 시점에 진단하나, IDE에 진단도구를 설치해 실시간 진단하는 프로젝트도 있다 (p.28).

## 6. 구현단계 보안약점 49개 — 대분류별 개관

대분류 정의 (PART4 절 도입부):
- **입력데이터 검증 및 표현** (p.180): "프로그램 입력값에 대한 검증 누락 또는 부적절한 검증, 데이터의 잘못된 형식지정, 일관되지 않은 언어셋 사용 등으로 인해 발생되는 보안약점으로 SQL 삽입, 크로스사이트 스크립트(XSS) 등의 공격을 유발할 수 있다."

## 7. 진단 수행 방법

실제로 소스코드를 받아 진단할 때의 권장 순서.

**1) 사전 준비**
- 진단 범위 확정: 신규개발은 소스코드 전체, 유지보수는 변경분 전체 (상용 SW 제외) (p.17).
- 언어·프레임워크 파악 후 라우팅: Java/JSP/Android → `secure-coding-java`, C/C++ → `secure-coding-c`.

**2) 정적분석 (도구 진단)**
- CC인증 진단도구로 49개 기준 전수 스캔 (p.17, p.28).
- 도구 결과는 "후보"다 — 그대로 보고서에 옮기지 말 것.

**3) 수동 확인 (미탐 보완)**
- 도구가 판단하기 어렵다고 원문이 명시한 항목은 반드시 수동 진단한다:
  - 18. 적절한 인증 없는 중요기능 허용 — 중요정보 여부는 진단원이 직접 파악 (p.317)
  - 19. 부적절한 인가 — 외부 시스템 권한 설정은 정적도구로 판단 곤란 (p.322)
  - 20. 중요한 자원에 대한 잘못된 권한 설정 — 중요자원 식별은 진단원 몫 (p.328)
  - 21. 취약한 암호화 알고리즘 — 자체 구현 알고리즘의 적절성 판단은 수동진단 필요 (p.333)
  - 22. 암호화되지 않은 중요정보 — 평문저장의 일반적 검사 기법은 존재하지 않음 (p.346)
  - 36. 오류 메시지 정보노출 — 민감정보 기준은 진단원이 판단 (p.421)
  - 45. 제거되지 않고 남은 디버그 코드 — J2EE 외에는 정적도구만으로 판단 곤란 (p.479)
  - 4. XSS(Stored) — DB 값이 사용자 입력으로 수정되는지는 정적도구로 판단 어려움 (p.219)

**4) 오탐 제거**
- 도구 검출 건마다 8절의 오탐 판별 표와 `references/weakness-49.md`의 항목별 "오탐 주의사항"을 대조하여 오탐을 걸러낸다.
- 오탐 제외 시에도 **판정 근거(원문 페이지)를 기록**해 둔다.

**5) 보고**
- 1차 진단보고서 필수 항목 (p.28): **검출 파일명 / 라인번호 / 보안약점명 / 원인설명 / 대응방법**.
- 2차 진단보고서: 위 항목 + **1차 검출 보안약점의 제거 여부** (p.28).
- 기준명·CWE·페이지는 `references/weakness-49.md`의 표기를 그대로 인용한다. 원문 인용 시 9절의 편집 오류에 주의.

보고서 기재 예시 (1차 진단, 형식 예):

| 파일명 | 라인 | 보안약점명 | 원인설명 | 대응방법 |
|---|---|---|---|---|
| `src/user/LoginDao.java` | 42 | SQL 삽입 (p.180) | 외부 입력 `id`를 문자열 결합으로 동적 쿼리 생성 | `PreparedStatement` 바인딩 변수로 변경 (p.180) |

## 8. 오탐(False Positive) 판별

원문 각 항목의 `오탐코드의 예`(취약하지 않다고 판정하는 코드)를 집약한 표. 도구 검출 건을 오탐 처리할 때 이 표의 근거 페이지를 인용하라.

| 약점 | 흔한 오탐 상황 | 오탐 판정 근거 |
|---|---|---|
| 1. SQL 삽입 | Hibernate `createQuery` + `setString`/`setParameter` 사용 | 파라미터 바인딩 수행 시 취약하지 않음 (p.192) |
| 2. 코드 삽입 | `eval()` 전에 위험 기호 제거(`preg_replace`)·검증 수행, 또는 동적 실행함수는 있으나 외부 입력값을 실행하지 않음 | 검증 후 사용 및 외부값 미실행은 안전 (p.198~199) |
| 3. 경로 조작 및 자원 삽입 | `getRealPath()`, `getContextPath()` 등 내장함수 값 사용 / 시스템 프로퍼티에서 가져온 값 사용 | 내장함수 소스는 안전. 시스템 프로퍼티는 오탐, 단 개별 사용 프로퍼티는 정탐 (p.208~210) |
| 4. XSS | 출력값이 숫자형 / `subString`으로 길이 제한 / 내부 고정값 / System 콘솔 출력 / JSTL `<c:out>`·`escapeXml` 사용 / 공격 문자열이 URL로만 이동 | 스크립트 실행 불가 조건 (p.217~219) |
| 5. OS 명령어 삽입 | 시스템 프로퍼티 기반 명령어 / `srcFile.getName()`처럼 경로문자·`..` 포함 불가 값 | 시스템 프로퍼티는 안전(개별 프로퍼티는 취약), 조작 불가 값은 안전 (p.230~231) |
| 6. 위험한 형식 파일 업로드 | 확장자 체크·필터링 존재 / `getOriginalFilename()` 리턴값을 저장하여 사용하지 않음 | 화이트리스트 검증 존재, 미사용 리턴값 (p.237~238) |
| 7. 신뢰되지 않는 URL 자동접속 | `getContextPath()` 결과로 리다이렉트 | 내장함수가 context path 리턴 — 안전한 URL (p.243) |
| 8. XXE | `DocumentBuilderFactory`/`SAXParserFactory` feature 제한, `SchemaFactory`·`Validator`·`XMLInputFactory`의 `setProperty()` 제한 설정 | 외부 엔티티 비활성화 설정 존재 (p.248~250) |
| 11. CSRF | 세션 저장 토큰 ↔ HIDDEN 필드 토큰 비교 후 일치 시에만 처리 | 토큰 검증 구현 시 오탐 판정 (p.274~275) |
| 12. SSRF | `169.254.169.254` 블랙리스트 필터링 + HTTP(S) 스킴 체크 | 안전 판정. 단, `isPrivateIP()` 등 내부대역 블랙리스트는 **우회 공격을 감안한 필터링인지 검토 후 판단** — 단순 오탐 처리 금지 (p.280~281) |
| 13. HTTP 응답분할 | 개행문자(`\r\n`) 필터링 후 쿠키 설정 / `getContextPath()` / Long·Integer 등 Numeric 값 | 개행 포함 불가 (p.288~289) |
| 14. 정수형 오버플로우 | `available()` 등 int 리턴 함수 / HTTP 헤더 한계값 존재 / 인자 개수의 한계 초과는 실현 희박 / 외부 입력값이 아님 | 정수 한계 초과 불가 (p.295~296) |
| 15. 보안기능 결정 부적절 입력값 | HIDDEN 필드 `price`를 쓰지 않고 서버 보유 가격으로 계산 | 외부값을 보안결정에 미사용 (p.301~302) |
| 19. 부적절한 인가 | 세션 저장 사용자 정보로 작업 권한 확인 후 권한 있을 때만 수행 | 서버 측 권한 검사 존재 (p.323~324) |
| 20. 잘못된 권한 설정 | 실행·쓰기 권한 제외, 읽기 권한만 부여 | 최소 권한 부여 (p.329) |
| 21. 취약한 암호화 알고리즘 | Base64 인코딩 사용 | 인코딩은 암호화가 아님(가시성·보관성 목적). **단, 개발자가 암호화 목적으로 사용했다면 취약 판정** (p.333~334) |
| 23. 하드코드된 중요정보 | 상수 문자열이 암호화 키가 아니라 **알고리즘명** 지정 | 키가 아닌 알고리즘명은 안전 (p.359) |
| 25. 적절하지 않은 난수 값 | `java.util.Random`·`java.security.SecureRandom` 사용 / Date 요소 등으로 자체 보완한 랜덤 키 생성 | 복잡도가 상대적으로 높음, 보완 구현 (p.368~369) |
| 26. 취약한 비밀번호 허용 | 로그인 시 비밀번호 **확인** 로직 | 저장이 아닌 확인 목적은 취약하지 않음 (p.374) |
| 27. 부적절한 전자서명 확인 | `new JarFile(f, true)` + `JarEntry.getCodeSigners()`로 주체 검증 | 서명·주체 모두 검증 (p.378) |
| 29. 영속 쿠키 정보 노출 | 쿠키 만료시간을 기능에 맞춰 최소로 설정 | 최소 만료시간 설정 (p.385) |
| 30. 주석 내 시스템 주요정보 | 주석에 "password"·"비밀번호" 등 텍스트만 있고 실제 비밀번호가 아님 | 실제 내용이 비밀번호가 아니면 안전 (p.389) |
| 34. TOCTOU 경쟁조건 | 실제로 경쟁조건이 성립하지 않음 / 동기화 구문·자체 pool 모듈 사용 | 동시 접근 불가 구조 (p.411~414) |
| 35. 종료되지 않는 반복문·재귀 | 같은 이름·다른 파라미터 함수 호출(오버로드, 재귀 아님) / 제어조건이 있는 재귀 | 재귀 판정은 함수명+파라미터 개수+자료형 일치 기준 (p.417~418) |
| 39. Null Pointer 역참조 | 널 미반환 함수(Javadoc 확인) / `throw` 후 코드 미도달 / 선행 문장에서 이미 역참조 발생 / OR 단축평가 / `catch`에서 `return` / JSP 내장객체 / `Integer` static 호출 / 단일 함수의 파라미터 널 / JRE 기본 패키지 생성자 | 역참조 미발생 조건 상세 규칙 (p.441~444) |
| 40. 부적절한 자원 해제 | `finally` 절에서 close / 함수 역할이 자원 리턴(해제는 호출자 책임) | 해제 흐름 보장 (p.453) |
| 43. 역직렬화 | HMAC으로 데이터 무결성 검증 후 역직렬화 | 무결성 검증 존재 (p.467~468) |
| 44. 잘못된 세션 데이터 노출 | JSP·서블릿 내 **내부 클래스** / `final` 필드(상수) / Spring 기반 eGov 프레임워크(IoC 인스턴스 관리) | 멤버필드 공유 문제 없음 (p.474~475) |
| 46. Public 메소드의 Private 배열 반환 | private가 아니고 `final`인 배열 | 취약하지 않음 (p.486) |
| 36. 오류 메시지 정보노출 | (주의) 원문에 `오탐코드의 예`가 있으나 설명 문구가 정탐과 동일하게 기재됨 | 문서 설명 불명확 — 민감정보 노출 여부로 직접 판단 (p.424) |

- 오탐 예가 원문에 없는 항목(9, 10, 16, 17, 18, 22, 24, 28, 31, 32, 33, 37, 38, 41, 42, 45, 47, 48, 49번)은 "문서 미기재"이며, 각 항목의 진단방법 원칙(필터링·검증 존재 시 안전 등)으로 판단한다 — `references/weakness-49.md` 참조.

## 10. OWASP Top 10:2025 ↔ 구현단계 49개 기준 매핑

> **OWASP Top 10:2025** 기준이다 (한국어 공식판 `top10.owasp.org/2025/ko/`, 조회일 2026-09-17) — **2021판이 아니다** (A03·A09·A10 은 2025 신설·개편 항목). Top 10 은 **리스크 분류 체계**이지 진단 기준이 아니다 — **제도 판정은 49개 기준으로 한다.** CWE 가 필요하면 이 표가 아니라 `references/weakness-49.md` 정본을 인용하라.

| Top 10:2025 | 항목명 | 대응 국내 기준번호 |
|---|---|---|
| A01:2025 | Broken Access Control | 11, 12, 18, 19, 20 |
| A02:2025 | Security Misconfiguration | 29, 45 |
| A03:2025 | Software Supply Chain Failures | **대응 없음** (32 가 인접) |
| A04:2025 | Cryptographic Failures | 21, 22, 23, 24, 25, 26, 31 |
| A05:2025 | Injection | 1, 2, 4, 5, 9, 10, 13 |
| A06:2025 | Insecure Design | 설계단계 기준 (SR1-1~SR4-1, 5절) |
| A07:2025 | Authentication Failures | 26, 33, 44 |
| A08:2025 | Software or Data Integrity Failures | 27, 32, 43 |
| A09:2025 | Security Logging and Alerting Failures | **대응 없음** |
| A10:2025 | Mishandling of Exceptional Conditions | 35, 36, 37, 38 |

- **A03·A09 는 국내 49개 기준의 순수 공백**이다. 특히 A09 는 방향이 반대다 — 국내 36번은 로그·오류 메시지의 정보 **노출 금지**를 보는데, A09 는 로깅·알림의 **부재** 자체를 취약으로 본다. 36번 준수가 A09 대응을 의미하지 않는다.
- 공백 영역의 보강 점검은 `owasp-masvs`(모바일)·`owasp-asvs`(웹·API)로 라우팅한다 — 구속력 없음 병기 원칙은 2절 참조.
