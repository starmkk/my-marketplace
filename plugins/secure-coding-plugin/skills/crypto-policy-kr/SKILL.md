# 암호 알고리즘 및 키 길이 정책 (KISA 2018) 레퍼런스 스킬

## 개요

이 스킬은 과학기술정보통신부 / 한국인터넷진흥원(KISA)이 발행한
**「암호 알고리즘 및 키 길이 이용 안내서」(KISA-GD-2018-0034, 2018.12 개정, 총 16페이지)** 를 근거로,
다음 판단을 내릴 때 사용한다.

- 코드 리뷰/보안 진단 시 **사용된 암호 알고리즘과 키 길이가 국내 권고 기준을 만족하는지** 판정
- 신규 설계 시 **어떤 알고리즘·키 길이를 선택할지** 권고
- **암호키 유효기간**(교체 주기) 설정 근거 제시
- SHA-1 / HAS-160 등 **용도별 사용 가능 여부** 정밀 판정 (과잉 지적 방지)

안내서의 요지: 국산 암호 알고리즘(SEED, HIGHT, ARIA, KCDSA 등)을 포함해
보안강도(112/128/192/256비트)에 따라 선택 가능한 암호 알고리즘의 종류·키 길이·유효기간을 제시하며,
**112비트 이상의 안전성을 가지는 알고리즘의 사용을 권고**한다. (p.03)

> ⚠️ **판본 주의**: 본 스킬의 근거는 **2018년 판본**이다. 이후 KISA/국정원 정책이 개정되었을 수 있으므로,
> 최신 규제 대응 시에는 반드시 현행 고시·안내서 최신판을 교차 확인하라.

## 한 줄 결론 (기본 권고선)

```
① 모든 암호 알고리즘은 보안강도 112비트 이상을 사용하라.
   (112비트 강도의 안전성 유지기간: 2011~2030년)

② 2030년 이후(예: 2035년)까지 쓸 공개키 암호는
   128비트 강도 = RSA(인수분해 기반) 3072비트 이상을 쓰라.
   (2018년 기준 2048비트도 안전하지만, 향후 활용 시기를
    고려해 3072비트 이상 권장 — p.14)
```

> 📌 **적용 범위 주의**: 이 안내서는 **알고리즘 선택과 키 길이**를 규정할 뿐,
> 운영모드·IV·비밀번호 저장(KDF)·난수 생성 등 **구현 수준의 안전성**은 다루지 않는다.
> 구현 단계 권고는 아래 [현행 모범사례 — 안내서 범위 밖 보완 권고](#현행-모범사례--안내서-범위-밖-보완-권고) 절을 따르라.

## 보안강도별 권고 키 길이 (〈표 6〉, p.10 — 핵심 종합표)

**보안강도**란 암호키/해시함수의 취약성을 찾아내는 데 소요되는 작업량을 수치화한 것으로
112, 128, 192, 256비트로 정의된다 (112비트 = 2^112번 계산 필요). (p.03)

| 보안강도 | 대칭키 암호<br>(보안강도) | 해시함수<br>(보안강도) | 인수분해(RSA)<br>(비트) | 이산대수<br>공개키(비트) | 이산대수<br>개인키(비트) | 타원곡선<br>(비트) | 안전성 유지기간 |
|---|---|---|---|---|---|---|---|
| **112 비트** | 112 | 112 | 2048 | 2048 | 224 | 224 | **2011년~2030년까지** |
| **128 비트** | 128 | 128 | 3072 | 3072 | 256 | 256 | **2030년 이후** |
| **192 비트** | 192 | 192 | 7680 | 7680 | 384 | 384 | **2030년 이후** |
| **256 비트** | 256 | 256 | 15360 | 15360 | 512 | 512 | **2030년 이후** |

판정 기준 예시:
- RSA 2048비트 = 112비트 강도 → 2030년까지 유효. **RSA 1024비트는 표에 없음 = 권고 미달.**
- ECDSA P-224 = 112비트 강도, P-256 = 128비트 강도.

## 권고 암호 알고리즘 (〈표 1〉, p.04~05)

### 국내 권고 (검증대상보호함수 · IT보안인증사무국 국내 표준 기반)

| 용도 | 국내 권고 알고리즘 (2018) |
|---|---|
| 대칭키 블록암호 | **SEED, HIGHT, ARIA(-128/192/256), LEA(-128/192/256)** |
| 해시함수 | SHA-224/256/384/512, SHA-512/224, SHA-512/256, SHA3-224/256/384/512, **LSH-224/256/384/512, LSH-512-224, LSH-512-256** |
| 공개키 — 키 공유 | DH, ECDH |
| 공개키 — 암·복호화 | **RSAES** |
| 공개키 — 전자서명 | RSA-PSS, **KCDSA, ECDSA, EC-KCDSA** |

> 국내 권고 외의 알고리즘을 사용할 경우, 국외 권고(안)을 참고하기를 권장함. (p.05 각주 1)

### 국외 권고 (요약)

| 용도 | NIST(미국, 2015) | CRYPTREC(일본, 2013) | ECRYPT(유럽, 2018) |
|---|---|---|---|
| 대칭키 블록암호 | AES, 3TDEA | AES, Camellia | AES, Camellia, Serpent |
| 해시함수 | SHA-2 계열, SHA-3 계열 | SHA-256/384/512 | SHA-2/SHA-3 계열, SHA3-shake128/256, Whirlpool-512, BLAKE 계열 |
| 공개키 — 키 공유 | DH, ECDH, MQV, ECMQV | DH, ECDH | ECIES-KEM, PSEC-KEM, RSA-KEM |
| 공개키 — 암·복호화 | RSA | RSA-OAEP | RSA-OAEP |
| 공개키 — 전자서명 | RSA, DSA, ECDSA | RSA-PSS, RSASSA-PKCS1(v1.5), DSA, ECDSA | RSA-PSS, ISO-9796-2 RSA-DS2, Schnorr, ECSchnorr, KDSA, ECKDSA, PV Signatures, XMSS |

- 국내 권고 대칭키는 SEED/HIGHT/ARIA/LEA로 한정된다. AES는 국외(NIST 등) 권고 알고리즘이다.
- 타원곡선 기반 권고 알고리즘 중 **암·복호화용은 없다** (키 공유·전자서명용만 존재). (p.09, p.14)
- 보안강도별 알고리즘 전체 목록은 `references/algorithm-tables.md`의 〈표 2〉~〈표 5〉를 참조.

## 사용 제한 알고리즘 — SHA-1, HAS-160 (〈표 3〉 각주, p.07)

안내서에 **명시적으로 기재된 사용 제한은 아래 두 건뿐**이다.
**용도에 따라 가능/불가가 갈리므로**, 코드 진단 시 아래 표대로 정확히 구분하라.
(예: HMAC-SHA1을 "SHA-1 사용 금지"로 일괄 지적하면 과잉 지적이다.)

| 알고리즘 | 단순해시용 | 전자서명용 | 메시지인증용 | 키유도용 | 난수생성용 | 근거 |
|---|---|---|---|---|---|---|
| **SHA-1** | ❌ 불가 | ❌ 불가 | ✅ 가능 | ✅ 가능 | ✅ 가능 | 충돌저항성이 80비트 강도를 제공하지 못함 (NIST SP 800-56 Rev.4) |
| **HAS-160** (국산) | ❌ 불가 | ❌ 불가 | ✅ 가능 | ✅ 가능 | ✅ 가능 | 충돌저항성이 112비트 강도를 제공하지 못함 |

- "단순해시용"에는 **패스워드의 안전한 저장**이 포함된다 (p.08). → **비밀번호 해시에 SHA-1/HAS-160 사용 불가.**
- SHA-1/HAS-160은 〈표 3〉(메시지인증/키유도/난수생성용)의 112·128비트 칸에만 등장하며, 〈표 4〉(단순해시/전자서명용)에는 등장하지 않는다.
- DES, 3DES, MD5, RC4 등에 대한 "금지 알고리즘 목록"은 **이 안내서에 존재하지 않는다** — 아래 "현행 모범사례" 절 참조.

## 암호키 유효기간 (〈표 7〉, p.11 — NIST SP 800-57 Part 1 Rev.4 기반)

| 키 종류 | | 송신자 사용기간 | 수신자 사용기간 |
|---|---|---|---|
| 대칭키 암호 알고리즘 | 비밀키 | **최대 2년** | **최대 5년** |
| 공개키 암호 알고리즘 | 암호화 공개키 | 최대 2년 | 최대 2년 |
| | 복호화 개인키 | 최대 2년 | 최대 2년 |
| | 검증용 공개키 | **최소 2년** | **최소 2년** |
| | 서명용 개인키 | 최대 2년 | 최대 2년 |

- 수신자의 비밀키 사용기간이 더 긴 이유: 수신 후 필요시 복호화할 수 있으므로 송신자보다 오래 사용 가능. (p.11 각주)
- 검증용 공개키만 "**최소** 2년"임에 주의 — 서명 검증은 서명 생성 이후에도 계속 필요하기 때문이다 (나머지는 모두 "최대").

## 선택 가이드 (의사결정)

| 상황 | 권고 (안내서 근거) |
|---|---|
| 국내 공공/규제 대응 프로젝트, 개인정보·금융정보 저장 | 대칭키: **SEED, HIGHT, ARIA, LEA** 중 선택 (112비트 이상). 키 유효기간 송신자 2년/수신자 5년. (p.12 활용 예) |
| 국제 호환이 필요한 경우 | 국내 권고 외 알고리즘은 국외 권고(NIST 등: AES 등)를 참고. (p.05 각주) |
| 비밀번호 저장 (일방향) | 단순해시용 해시함수 중 112비트 이상: **SHA-224 이상, SHA-3 계열, LSH 계열**. SHA-1/HAS-160 불가. (p.13 활용 예) |
| 2025년까지 사용할 대칭키 암호 | 112비트 이상이면 충분 → SEED, HIGHT, ARIA, LEA 등. (p.13 활용 예) |
| 2035년까지 사용할 공개키 암·복호화 | 128비트 강도 필요 → **RSAES 3072비트 이상** (타원곡선 기반 암·복호화용 권고 알고리즘 없음). 키 유효기간 최대 2년. (p.14 활용 예) |
| 전자서명 (국산 우선) | **KCDSA(이산대수), EC-KCDSA/ECDSA(타원곡선), RSA-PSS(인수분해)**. 장기 사용 시 128비트 강도 키 길이(3072/256비트) 적용. |
| 키 공유(키 교환) | DH(3072비트 이상 권장), ECDH(256비트 이상 권장 — 128비트 강도 기준). |

판단 절차 (안내서 4장 활용 예의 공통 흐름):
1. 〈표 6〉에서 목표 사용 시점 기준 필요한 보안강도 확인 (2030년까지 → 112비트, 2030년 이후 → 128비트 이상)
2. 용도(양방향/일방향/공개키)에 맞는 표(〈표 2〉/〈표 3〉/〈표 4〉/〈표 5〉)에서 해당 보안강도의 알고리즘 선택
3. 〈표 7〉로 키 사용 유효기간 설정

## 빠른 판정 체크리스트 (코드 진단용)

아래 판정은 모두 위 표(〈표 2〉~〈표 7〉)에서 직접 도출된다.

| 발견된 사용례 | 판정 | 근거 |
|---|---|---|
| `RSA 1024비트` 키 생성 | ⚠️ 권고 미달 | 〈표 6〉 최저선이 2048비트(112비트 강도) — 1024비트는 표에 없음 |
| `RSA 2048비트` | ✅ 2030년까지 유효 | 112비트 강도, 안전성 유지기간 2011~2030년 |
| `RSA 3072비트` | ✅ 2030년 이후 장기 사용 가능 | 128비트 강도 |
| `ECDSA P-256` 서명 | ✅ 국내 권고 (128비트 강도) | 〈표 1〉/〈표 5〉 전자서명용 ECDSA, 타원곡선 256비트 |
| `DH 2048비트` 키 교환 | ✅ 2030년까지 유효 (개인키 224비트 이상 확인) | 이산대수 공개키 2048 / 개인키 224비트 = 112비트 강도 |
| 비밀번호를 `SHA-1`으로 해시 | ❌ 불가 | 단순해시(패스워드 저장) 용도 — 〈표 3〉 각주 1 |
| `HMAC-SHA1` 메시지 인증 | ✅ 해시 자체는 사용 가능 (메시지인증용) — 단, HMAC 구성 자체는 안내서 미기재. 신규 설계는 HMAC-SHA256 이상 권장 | 〈표 3〉 각주 1 + "현행 모범사례" 절 4항 참조 |
| `SHA-1` 기반 전자서명 (예: 인증서 서명) | ❌ 불가 | 〈표 3〉 각주 1 (충돌저항성 미달) |
| `HAS-160` 전자서명 | ❌ 불가 (메시지인증/키유도/난수생성용만 가능) | 〈표 3〉 각주 2 |
| `SEED`, `ARIA-128`, `LEA-128`, `HIGHT` 대칭 암호화 | ✅ 국내 권고 (112비트 이상 강도) | 〈표 2〉 국내 열 |
| `AES-128` 대칭 암호화 | ✅ 국외(NIST 등) 권고 — 국내 권고 목록에는 없음 | 〈표 1〉/〈표 2〉, p.05 각주 1 |
| 대칭 비밀키를 5년 넘게 교체 없이 사용 | ⚠️ 유효기간 초과 | 〈표 7〉 송신자 최대 2년 / 수신자 최대 5년 |
| 192비트 강도가 필요한데 `SEED`/`HIGHT` 사용 | ⚠️ 강도 미달 | 〈표 2〉 192비트 칸의 국내 알고리즘은 ARIA-192/256, LEA-192/256뿐 |

주의: `DES`, `3DES`, `MD5`, `RC4` 발견 시 — **이 안내서를 근거로 지적하지 말 것.**
해당 항목의 금지 근거는 이 안내서에 없다. 지적 시에는 아래 "현행 모범사례" 절 1항에
명시된 출처(NIST SP 800-131A Rev.2, 「소프트웨어 보안약점 진단가이드(2021)」 등)와
`secure-coding-kr` 스킬의 '취약한 암호화 알고리즘 사용' 진단기준을 근거로 인용하라.

## 현행 모범사례 — 안내서 범위 밖 보완 권고

아래 항목들은 **본 안내서(2018, 16p)에 기재되어 있지 않다.**
따라서 이 절의 내용을 "KISA 키 길이 안내서 위반"으로 지적해서는 안 되며,
제도 대응·감사 지적 시에는 각 항목에 명시된 출처 문서를 정확히 인용하라.

다만 **안내서에 없다는 이유로 구현을 흐릿하게 남겨두지 말 것** — 어느 권고가 우선하는지는
판단의 **용도(맥락)** 에 따라 갈린다. 아래 구분을 지켜라.

- 📕 **제도 판정** (적합/부적합 판정, 감사 지적 대응, 검증 신청): **해당 시점에 효력 있는 고시·안내서가 구속력 있는 기준**이다.
  전자정부 진단·감사 자리에서는 2018년 안내서(및 진단가이드 2021)를 그대로 인용하라 —
  "NIST 최신 권고가 다르다"는 것은 제도 판정을 뒤집는 사유가 되지 않는다.
- ✅ **신규 설계·코드 리뷰** (구속력 없는 기술 판단): 아래 현행 모범사례를 그대로 적용한다 (항목별 출처·기준시점 병기).
- 두 판단이 어긋나는 항목은 **양쪽을 병기**하고, 각 결론이 어느 맥락(제도 판정 / 기술 권고)의 것인지 명시하라.

### 1. 취약 알고리즘 — 쓰지 말 것

**권고**: 아래 알고리즘·구성은 신규 설계에서 사용 금지, 기존 시스템에서는 교체 계획 수립.

| 금지 대상 | 위험 이유 (한 줄) | 대체 |
|---|---|---|
| DES | 키 56비트 — 전수조사로 수 시간 내 해독 가능 | AES/ARIA/SEED/LEA (128비트 이상) |
| 3DES (2TDEA/3TDEA) | NIST SP 800-131A Rev.2에서 2023년 말 이후 암호화 용도 사용 불허(disallowed), 64비트 블록으로 Sweet32 공격에 취약 | AES/ARIA (128비트 블록) |
| MD5 | 충돌 생성이 실용화됨 (초 단위) — 무결성·서명·비밀번호 어디에도 부적합 | SHA-256 이상 (용도별 아래 3·4항) |
| SHA-1 (단순해시/서명) | 실제 충돌 공격 시연됨 (SHAttered, 2017) — 안내서도 이 용도는 불가로 명시 (p.07) | SHA-256 이상, SHA-3 |
| RC4 | 키스트림 통계 편향 — TLS 사용 금지 (RFC 7465) | AEAD (AES-GCM 등) |
| ECB 모드 | 동일 평문 블록 → 동일 암호문 (패턴 노출) | GCM 등 AEAD (아래 2항) |
| RSA 1024비트 이하 | 인수분해 현실화 영역 — 안내서 〈표 6〉 최저선(2048)에도 미달 | RSA 2048 이상, 장기 사용 3072 이상 |
| RSA PKCS#1 v1.5 **암호화** | 패딩 오라클 공격 (Bleichenbacher 계열) | RSA-OAEP (RFC 8017) |

> ⚠️ 위 금지 목록은 **이 안내서(2018)를 근거로 지적하지 말 것.** 안내서에 명시된 사용 제한은
> SHA-1·HAS-160 두 건뿐이다 (〈표 3〉 각주, p.07). 제도 대응 시에는 아래 출처를 인용하라.

**출처**: NIST SP 800-131A Rev.2 (Transitioning the Use of Cryptographic Algorithms and Key Lengths, 2019), 「소프트웨어 보안약점 진단가이드(2021)」 '취약한 암호화 알고리즘 사용' (→ `secure-coding-kr` 스킬), RFC 7465 (RC4 금지), RFC 8017 (PKCS#1 v2.2)
**본 안내서 위치**: 미기재 (SHA-1/HAS-160 제한만 p.07 각주에 존재)

### 2. 블록암호 운영모드 · IV · 패딩

**권고**: **AEAD 모드(AES-GCM, ARIA-GCM, ChaCha20-Poly1305)를 기본값**으로 사용하라.
기밀성과 무결성을 한 번에 제공하므로 별도 MAC 구성 실수를 원천 차단한다.

| 상황 | 권고 | 피할 것 |
|---|---|---|
| 일반 데이터 암호화 (기본) | AES-GCM / ARIA-GCM — IV는 **96비트(12바이트) 고유값**, 카운터 또는 CSPRNG 생성 | ECB (절대 금지), 모드 미지정 |
| GCM IV 관리 | 동일 키로 IV **재사용 절대 금지** — 재사용 시 인증키 노출로 위·변조 가능 (치명적) | 고정 IV, 시각 기반 IV |
| AEAD 사용 불가 환경 | CBC + **암호문마다 새 랜덤 IV** + 별도 HMAC (**Encrypt-then-MAC** 순서) | MAC 없는 CBC (패딩 오라클), MAC-then-Encrypt |
| 패딩 | AEAD는 패딩 불필요. CBC는 PKCS#7 + 복호화 오류 메시지 비노출 | 패딩 오류를 구분 가능한 응답으로 반환 |

> ⚠️ **구현 함정**: Java `Cipher.getInstance("AES")` 처럼 모드를 지정하지 않으면
> 구현체 기본값(대부분 **`AES/ECB/PKCS5Padding`**)이 적용된다. 반드시
> `"AES/GCM/NoPadding"` 처럼 모드·패딩까지 완전한 변환 문자열을 명시하라. C/기타 언어도 동일.

**출처**: NIST SP 800-38A (운영모드), NIST SP 800-38D (GCM/GMAC — IV 요건 포함), OWASP Cryptographic Storage Cheat Sheet
**본 안내서 위치**: 미기재 — 알고리즘 종류·키 길이·유효기간만 다룸

### 3. 비밀번호 저장 — 단순 해시 금지, 전용 KDF 사용 (가장 중요)

**권고**: 비밀번호는 반드시 **비밀번호 전용 KDF(스트레칭 해시)** 로 저장하라.
우선순위: **Argon2id > scrypt > bcrypt > PBKDF2-HMAC-SHA256**.

| KDF | 권장 파라미터 (OWASP, 2023년 기준) | 비고 |
|---|---|---|
| **Argon2id** (1순위) | 메모리 m=19MiB, 반복 t=2, 병렬 p=1 이상 | 메모리 하드 — GPU/ASIC 공격 저항 최고 |
| **scrypt** (2순위) | N=2^17(128MiB), r=8, p=1 이상 | Argon2 미지원 환경 대안 |
| **bcrypt** (3순위) | cost(work factor) ≥ 10 | 입력 72바이트 제한 주의 |
| **PBKDF2-HMAC-SHA256** (4순위) | 반복 600,000회 이상 | FIPS 준수 요구 환경에서 선택 |

- **salt**: 사용자별 고유 랜덤 **16바이트 이상** (CSPRNG 생성). 재사용·고정 금지.
- **pepper**(선택): DB 외부(HSM/KMS/환경변수)에 보관하는 전역 비밀값 — 적용 시 방어층 추가.
- ⚠️ 위 파라미터 수치의 기준 시점은 **OWASP Password Storage Cheat Sheet 2023년판**이다.
  OWASP 권고치는 하드웨어 발전에 따라 **주기적으로 상향**되므로 적용 시 최신판을 확인하라.

> ⚠️ **안내서와의 혼동 주의 — 반드시 읽을 것**: 안내서 p.08·p.13은 "패스워드의 안전한 저장"을
> **단순해시용** 해시함수 용도로 분류하고 SHA-256 등을 선택 가능하다고 서술한다. 이는
> *어떤 해시함수가 충분한 안전강도(충돌저항성)를 갖는가*를 다룰 뿐, *스트레칭(고의적 저속화)의
> 필요성*은 다루지 않는다. **salt 없는 단순 SHA-256/SHA-512 1회 해시로 비밀번호를 저장하는 것은
> 현행 기준 부적합**하다 — GPU로 초당 수십억 회 대입이 가능하기 때문이다.
> SHA-256은 위 KDF **내부의 해시 원시함수**(예: PBKDF2-HMAC-SHA256)로 쓰일 때만 적절하다.

**출처**: OWASP Password Storage Cheat Sheet (파라미터 수치: 2023년 기준), NIST SP 800-63B (Digital Identity Guidelines — memorized secret 저장 요건)
**본 안내서 위치**: 미기재 (p.13 활용 예 2는 해시함수 선택 기준까지만 제시 — 스트레칭 미언급)

### 4. 메시지 인증 (MAC)

**권고**: **HMAC-SHA256 이상**을 사용하라. AEAD(GCM 등)를 사용 중이면 별도 MAC은 불필요하다.

| 상황 | 권고 | 피할 것 |
|---|---|---|
| 메시지 무결성·인증 | HMAC-SHA256 / HMAC-SHA512, 또는 CMAC-AES | 해시 단독(`SHA256(key‖msg)` — 길이확장 공격), HMAC-MD5 |
| AEAD 사용 중 | 별도 MAC 불필요 (GCM 태그가 인증 제공) | AEAD 위에 중복 MAC 구성 |
| MAC 검증 비교 | **상수시간 비교** 필수 — Java `MessageDigest.isEqual()`, OpenSSL `CRYPTO_memcmp()`, Python `hmac.compare_digest()` | `==`, `equals()`, `memcmp()` (타이밍 공격) |
| MAC 키 | 암호화 키와 **분리된 독립 키** 사용 | 암호화 키 재사용 |

> 안내서는 SHA-1의 **메시지인증용** 사용을 허용한다 (〈표 3〉 각주, p.07). 따라서 기존 코드의
> HMAC-SHA1을 "안내서 위반"으로 지적하는 것은 과잉 지적이다. 그러나 **안내서 허용 ≠ 최선** —
> **신규 설계에서는 HMAC-SHA256 이상**을 사용하라.

**출처**: FIPS 198-1 (HMAC), NIST SP 800-107 Rev.1 (해시 알고리즘 보안강도별 사용 권고)
**본 안내서 위치**: 미기재 — "메시지인증용 해시함수" 용도 분류만 존재 (HMAC 등 구성 명칭 없음)

### 5. 난수 생성

**권고**: 암호학적 용도(키, IV, salt, 토큰, 세션 ID 등)의 난수는 반드시 **OS CSPRNG 기반**으로 생성하라.

| 환경 | 권고 | 피할 것 (예측 가능 — 금지) |
|---|---|---|
| Java | `SecureRandom` (가능하면 `SecureRandom.getInstanceStrong()`) | `java.util.Random`, `Math.random()`, `System.currentTimeMillis()` 시드 |
| C / POSIX | `getrandom(2)`, `/dev/urandom` 읽기 | `rand()`, `srand(time(NULL))`, `random()` |
| OpenSSL | `RAND_bytes()` | 자체 구현 PRNG |
| Python | `secrets` 모듈, `os.urandom()` | `random` 모듈 |

- 시각·PID 등 **예측 가능한 값으로 시드를 직접 설정하지 말 것** — CSPRNG는 OS 엔트로피로 자동 시드된다.
- NIST 승인 DRBG(Hash_DRBG, HMAC_DRBG, CTR_DRBG)를 내부적으로 사용하는 검증된 라이브러리를 쓰고, 직접 구현하지 말 것.

**출처**: NIST SP 800-90A Rev.1 (DRBG), 「소프트웨어 보안약점 진단가이드(2021)」 '예측 가능한 난수 사용' (→ `secure-coding-kr` 스킬)
**본 안내서 위치**: 미기재 — "난수생성용 해시함수" 용도 분류만 존재

### 6. TLS 설정

**권고**: **TLS 1.2 이상**(가능하면 **TLS 1.3**)만 허용하고, 인증서 검증을 절대 비활성화하지 말라.

| 항목 | 권고 | 피할 것 |
|---|---|---|
| 프로토콜 버전 | TLS 1.3 우선, 최소 TLS 1.2 | SSLv2/v3, TLS 1.0/1.1 |
| Cipher suite | AEAD 기반 (예: `TLS_AES_128_GCM_SHA256`, ECDHE + AES-GCM) | NULL/EXPORT/anon 계열, RC4, 3DES, CBC+SHA-1 조합 |
| 키 교환 | ECDHE (전방향 안전성) | 정적 RSA 키 교환 |
| 인증서 검증 | 체인·유효기간·**호스트네임 검증 모두 활성** | `TrustAllCerts`, `verify=False`, `HostnameVerifier` 무력화 (개발 편의라도 금지) |

**출처**: NIST SP 800-52 Rev.2 (Guidelines for the Selection, Configuration, and Use of TLS Implementations)
**본 안내서 위치**: 미기재 — 프로토콜·전송계층 설정은 안내서 범위 밖
