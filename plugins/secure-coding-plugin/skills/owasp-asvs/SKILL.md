# OWASP ASVS 웹·API 보안 검증 레퍼런스 스킬

> 근거 문서: **OWASP Application Security Verification Standard (ASVS) 5.0.0**(릴리스 2025-05-30, 17챕터 / 345요구사항) · 공식 한국어 PDF **103페이지** 존재(제목 "애플리케이션 보안 검증 표준") · 라이선스 **CC BY-SA 4.0** · 조회일 **2026-09-17**.
> **인용 규약**: ASVS 는 요구사항 ID(`V3.4.3` 형식 — `V<챕터>.<섹션>.<순번>`)로 지칭하고 버전(`ASVS 5.0.0`)·조회일을 병기한다. 공식 한국어 PDF 가 있으므로 `(ko p.N)` 페이지 병기가 **가능**하지만, 영문 원본과 한국어판의 페이지가 다르므로 **어느 판본 기준인지 반드시 명시**한다. 이 규약은 기존 5종 스킬의 `(p.N)` 원문 페이지 병기 관례를 대체하는 예외이며, `owasp-masvs` 의 ID 병기 규약과 동일 방침이다.
> ⚠️ **버전 고정**: 이 스킬의 모든 수치·ID 는 GitHub 태그 **`v5.0.0`** 기준이다. main 브랜치는 이미 다를 수 있다 — 요구사항 원문 조회 시 반드시 태그로 고정하라.

## 1. 개요

### 1.1 ASVS 5.0.0 규모

| 항목 | 값 |
|---|---|
| 챕터 | 17개 (V1~V17) |
| 요구사항 | **345개** (73개 섹션) |
| 레벨 분포 | **L1 70개(20%) · L2 183개 · L3 92개** |
| 릴리스 | v5.0.0 (2025-05-30) |
| 한국어판 | 공식 한국어 PDF 103p |

- ASVS 는 웹 애플리케이션·API 의 보안 요구사항을 레벨별로 정의한 **검증 표준**이다. 모바일 앱은 별도 표준(MASVS)이 담당한다 → `owasp-masvs`.
- **이 스킬의 성격**: OWASP ASVS 전체를 담은 레퍼런스가 아니라, **국내 기준(설계단계 20개·구현단계 49개)의 공백을 메우는 보완재**다. 국내 기준이 이미 덮는 영역(인젝션·암호화·세션 등)은 기존 스킬로 라우팅하고, 이 스킬은 국내 기준으로 지적할 수 없는 영역(§6)과 국내 기준과 상충하는 항목(§7)을 중심으로 다룬다.
- **이 스킬은 제도 판정 근거가 아니다.** 전자정부법 체계의 진단·검증 판정은 📕 `secure-coding-kr`(진단가이드)·`mobile-app-verify` 원문 기준을 따른다. ASVS 근거 지적에는 반드시 요구사항 ID 와 **"구속력 없음"** 을 병기한다.
- frontmatter 에 기존 5종과 달리 `관련 스킬:` 블록이 없는 것은 **의도된 예외**다 — frontmatter 예산(850자) 제약하에서 `경계:` 줄이 라우팅을 대신한다 (설계문서 쟁점 1 결정, `owasp-masvs` 와 동일).

### 1.3 버전 고정 경고 ⚠️

- 요구사항 원문·전수 데이터는 공식 구조화 JSON(flat.json)으로 제공된다 — 조회 시 **태그 `v5.0.0` 경로**를 쓴다:
  `https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json`
- 상류 저장소가 갱신되면 이 스킬의 수치는 낡는다. 인용 시 반드시 "ASVS 5.0.0 / 2026-09-17 조회" 를 병기하라.

### 1.4 flat.json 조회 레시피 (✅ 방법 예시)

flat.json 은 `{"requirements": [...]}` 구조이며 항목 필드는 `chapter_id` · `chapter_name` · `section_id` · `section_name` · `req_id` · `req_description` · `L`(값 `"1"`/`"2"`/`"3"`) 이다 (v5.0.0 실측, 2026-09-17).

```bash
# 태그 고정판 내려받기 (main 아님 — §1.3)
curl -sL "https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/docs_en/\
OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json" -o asvs-5.0.0.json

# 예: V10(OAuth·OIDC) 요구사항의 ID·레벨·요지 추출
python3 -c "
import json
for r in json.load(open('asvs-5.0.0.json'))['requirements']:
    if r['chapter_id'] == 'V10':
        print(r['req_id'], 'L'+r['L'], r['req_description'][:60])
"
```

- 공백 7개 챕터(§6)의 로컬 색인은 `references/asvs-17-chapters.md` 가 담당한다 — 원문 전문이 필요할 때만 flat.json 을 받는다.

## 2. 4.0.3 → 5.0.0 마이그레이션 경고 ⭐

4.0.3 기준 자료·보고서·체크리스트를 그대로 쓰면 안 된다. 5.0.0 은 부분 개정이 아니라 **사실상 재편**이다.

| 변경 사실 | 내용 (📋 원문 수치) |
|---|---|
| 생존 항목 극소 | 4.0.3 의 286개 중 **11개만 무변경 생존** ("only 11 remain unchanged"). 5.0.0 의 345개 = 신설 189 + 수정 130 + 자구 수정 15 + 이동 11 |
| 대량 제거 | **109개(38%) 가 독립 요구사항에서 제거** — 단순 삭제 50 + 중복 제거 28 + 타 항목 병합 31 |
| V1 Architecture 삭제 | 📋 "The former V1 Architecture chapter has been removed." — 일부는 표준 범위 밖으로, 나머지는 타 챕터로 재배치 |
| L1 비중 급감 | **46%(128/278) → 20%(70/345)** |
| 레벨 기준 변경 | "블랙박스 검증 용이성" → **"위험 감소 효과 + 구현 노력"** (§4) |

### 2.1 ⚠️ V1 기호 재사용 함정

- 5.0.0 의 **V1 은 「Encoding and Sanitization」** 이다. 4.0.3 의 V1 「Architecture」와 **전혀 다른 챕터**다 — 4.0.3 V1 은 삭제되었고 `V1` 이라는 기호만 재사용되었다.
- ❌ 구버전 보고서의 "V1.x" 인용을 5.0.0 요구사항으로 번역 없이 옮기면 아키텍처 항목이 인코딩 항목으로 뒤바뀐다. 4.0.3 ID 를 만나면 반드시 판본을 확인하고, 5.0.0 ID 로 재조회한 뒤 인용하라.

빠른 판본 판별 신호:

| 문서에서 보이는 신호 | 판본 |
|---|---|
| "V1 = Architecture" 서술 | 4.0.3 계열 |
| "V1 = Encoding and Sanitization", 17챕터·345개 | 5.0.0 |
| 요구사항 총수 286(또는 활성 278)·"L1 128개" 통계 | 4.0.3 계열 |
| "L1 70개(20%)"·V9/V10/V17 챕터 존재 | 5.0.0 (V17 WebRTC 는 5.0.0 체계) |

### 2.2 ⚠️ 286 vs 278 분모 차이

- 4.0.3 원문에는 286개 항목이 있으나 그중 **8개는 4.0.3 자체에서 이미 `[DELETED, ...]` 로 표기된 자리표시(tombstone)** 다. 실질 활성 요구사항은 **278개**이고, 5.0 매핑 문서는 278개만 대상으로 한다.
- "286개 중 11개 생존" 과 "L1 128/278" 은 **분모가 다르다** — 둘 다 원문 표현이므로, 인용할 때 어느 분모인지 반드시 밝혀라.

### 2.3 구버전 산출물을 만났을 때의 대응 절차

4.0.3 기준 점검표·보고서·보안 요구사항 문서가 남아 있는 조직은 다음 순서로 처리한다.

1. **판본 식별** — 문서의 요구사항 ID 가 어느 판본인지 확인한다. "V1 = Architecture" 로 서술돼 있으면 4.0.3 계열이다 (§2.1 기호 함정).
2. **항목 단위 매핑 조회** — 공식 매핑 파일(`5.0/mappings/mapping_v4.0.3_to_v5.0.0.yml` · `mapping_v5.0.0_to_v4.0.3.yml`, 태그 `v5.0.0`)로 각 항목의 이동·수정·삭제 여부를 확인한다. 총량 기준 태그 집계: 5.0.0 의 345개 = ADDED 189 + MODIFIED 130 + GRAMMAR 15 + MOVED 11, 제거 109개 = 단순 삭제 50 + 중복 제거 28 + 병합 31.
3. **삭제 항목 처리** — 4.0.3 에만 있고 5.0.0 에서 제거된 항목(109개)을 근거로 한 지적은 "ASVS 5.0.0 기준 아님"을 명시하거나 현행 ID 로 대체한다.
4. **레벨 재평가** — 4.0.3 의 L1/L2/L3 배정은 5.0.0 과 기준이 다르다(§4). 구 레벨 표기를 그대로 옮기지 말 것.
5. **분모 명시** — 마이그레이션 통계를 인용할 때 286(원문 항목 수) / 278(활성 요구사항) 어느 쪽인지 밝힌다 (§2.2).

## 4. L1/L2/L3 재정의

### 4.1 무엇이 바뀌었나

| 구분 | 4.0.3 | 5.0.0 |
|---|---|---|
| 레벨 선정 기준 | 블랙박스 검증 용이성 | 📋 **위험 감소 효과 + 구현 노력** ("level decisions were made primarily based on risk reduction and also keeping in mind the effort to implement") |
| L1 비중 | 46% (128/278) | **20% (70/345)** |

### 4.2 레벨별 규모와 성격 (v5.0.0 실측)

| 레벨 | 요구사항 수 | 비중 | 성격 (기준 문장에서 도출) |
|---|---|---|---|
| L1 | 70 | 20% | 위험 감소 효과가 크고 구현 노력이 낮은 최우선 항목 |
| L2 | 183 | 53% | 최다 분포 — 표준적 점검 범위의 중심 |
| L3 | 92 | 27% | 고보증 대상 — V3(12개)·V11(10개)에 상대적으로 집중 |

### 4.3 실무적 함의

- ❌ **"L1 = 펜테스트로 잡히는 것"이라는 통념은 5.0.0 에서 더 이상 성립하지 않는다.** 4.0.3 의 L1 은 "블랙박스로 검증 가능한 항목" 성격이 강했지만, 5.0.0 의 L1 은 "위험 감소 효과가 크고 구현 노력이 낮은 최우선 항목"으로 재정의되었다.
- L1 비중이 절반 이하로 줄었으므로(46%→20%), **"L1 만 만족" 은 4.0.3 시절보다 훨씬 좁은 범위**다. 4.0.3 기준 "L1 달성" 이력을 5.0.0 의 L1 달성과 동치로 보고하면 안 된다.
- V16(로깅·에러처리)은 **L1 이 0개**다 — L1 범위만 점검하면 로깅 요구사항 전체가 점검 대상에서 빠진다. V17(WebRTC)도 L1 0개다.
- 챕터별 L1 분포 편차가 크다 — V6(13개)·V1(8개)·V3(8개)에 몰려 있고 V13 은 1개, V16·V17 은 0개다. "L1 준수" 표명은 챕터별로 실질 의미가 크게 다르므로, 표명 시 챕터 범위를 함께 밝혀라.
- ✅ 레벨 선택은 대상 앱의 위험도·데이터 민감도에 따르되, 레벨과 무관하게 국내 제도 검증 대상이면 📕 국내 기준(49개·20개)이 우선 적용된다.

## 5. 국내 설계단계 20개 대응

국내 「소프트웨어 보안약점 진단가이드」(2021.11) 분석·설계단계 보안설계 기준 20개(SR1-1~SR4-1, `secure-coding-kr` §5)와 ASVS 챕터의 대응 개요다. **SR 번호별 20행 상세 대응표는 `references/asvs-sr20-mapping.md`** 참조.

| ASVS 챕터 | 국내 SR 대응 |
|---|---|
| V1 Encoding and Sanitization · V2 Validation and Business Logic | SR1-1~SR1-9 (입력데이터 검증 및 표현) |
| V5 File Handling | SR1-10 (업로드·다운로드 파일 검증) |
| V6 Authentication | SR2-1(인증 대상 및 방식)·SR2-2(인증 수행 제한)·SR2-3(비밀번호 관리) — ⚠️ §7 충돌 |
| V7 Session Management | SR4-1 (세션통제) |
| V8 Authorization | SR2-4 (중요자원 접근통제) |
| V11 Cryptography | SR2-5(암호키 관리)·SR2-6(암호연산) — 알고리즘·키 길이 판정은 `crypto-policy-kr` |
| V12 Secure Communication | SR2-8 (중요정보 전송) |
| V14 Data Protection | SR2-7 (중요정보 저장) |
| V16 Security Logging and Error Handling | SR3-1(예외처리) — ⚠️ **에러처리만 대응. 로깅은 국내 설계기준에 없음** |
| **V3 · V4 · V9 · V10 · V13 · V15 · V17** | **대응 없음 — 공백 7개 (§6)** |

- ⚠️ **SR3-1 비대칭**: V16 챕터명은 「Security Logging **and** Error Handling」이지만 국내 SR3-1(예외처리)은 에러처리 측면만 대응한다. 보안 로깅 요구는 국내 설계단계 기준에 대응 항목이 없다 — `secure-coding-kr` §10 의 A09(로깅·알림 실패) 공백과 같은 맥락이다.
- 대응이 "있다"는 것은 챕터 주제 수준의 대응이지 요구사항 1:1 동치가 아니다. 국내 기준이 덮는 챕터에서도 개별 요구사항 수준에서는 국내 기준에 없는 항목이 존재할 수 있다 — 단정이 필요하면 flat.json 원문(§1.3)을 확인하라.

### 5.1 표준 점검 워크플로

```
① 점검 성격 구분          — 📕 제도 진단·검증이면 `secure-coding-kr` 기준 우선,
                            자율 보강 점검이면 이 스킬 계속
② 레벨 결정 (§4)          — 위험 감소 + 구현 노력 기준. 4.0.3 통념 금지
③ 챕터 필터 (§3, 위 표)   — 국내 SR 대응 챕터는 기존 스킬 기준으로,
                            공백 7개 챕터(§6)는 이 스킬로 점검
④ 요구사항 조회 (§1.3)    — 태그 v5.0.0 flat.json 에서 해당 챕터·섹션 추출
                            (공백 7개는 references/asvs-17-chapters.md 가 로컬 색인)
⑤ 기록 (§6.8)             — 요구사항 ID·버전·판본·조회일·"구속력 없음" 병기
```

## 6. 국내 공백 7개 챕터 ⭐

이 절이 이 스킬의 핵심 부가가치다. 아래 7개 챕터(합계 **144개 요구사항**)는 국내 설계단계 20개 기준에 대응 항목이 전무하다. 용어에 주의하라 — 이는 국내 기준의 "결함 목록"이 아니라 **국내 기준을 근거로는 지적할 수 없는 영역**이다(**미기재 ≠ 부적합**). 이 영역을 점검하려면 이 스킬(ASVS 요구사항 ID·구속력 없음 병기)을 사용한다.

공통 배경: 국내 설계단계 20개는 4개 유형(입력데이터 검증 10 · 보안기능 8 · 에러처리 1 · 세션통제 1)으로 구성되어, 브라우저 보안 메커니즘·API 프로토콜·토큰 형식·인가 위임·구성 관리·아키텍처·실시간 미디어라는 **유형 자체가 없다**. 요구사항 수준 상세는 `references/asvs-17-chapters.md` 참조.

### 6.1 V3 Web Frontend Security (31개 — L1 8 · L2 11 · L3 12)

- 섹션: 3.1 Documentation · 3.2 Unintended Content Interpretation · 3.3 Cookie Setup · 3.4 Browser Security Mechanism Headers · 3.5 Browser Origin Separation · 3.6 External Resource Integrity · 3.7 Other Browser Security Considerations.
- 다루는 것: **CSP · CORS · 쿠키 속성(✅ SameSite 등) · SRI(외부 리소스 무결성) · 브라우저 출처 분리** 등 브라우저 보안 메커니즘 전반.
- 왜 국내에 없는가: 국내 20개 기준에는 브라우저 보안 헤더·쿠키 속성 표준화 유형이 없다. SR4-1(세션통제)은 세션 설계를 다루지만 쿠키 보안 속성·응답 헤더 수준의 요구는 아니다.
- 17챕터 중 **L3 요구사항이 가장 많은 챕터(12개)** — 프런트엔드 심층 방어가 고보증 레벨에 집중돼 있다.
- ✅ 점검: 응답의 CSP 정책 존재·엄격성, CORS 허용 출처 목록의 최소화, 세션 쿠키의 Secure·HttpOnly·SameSite 속성, 외부 스크립트·스타일의 SRI 해시 적용, 클릭재킹 대응 헤더.

### 6.2 V4 API and Web Service (16개 — L1 2 · L2 8 · L3 6)

- 섹션: 4.1 Generic Web Service Security · 4.2 HTTP Message Structure Validation · 4.3 GraphQL · 4.4 WebSocket.
- 다루는 것: HTTP 메시지 구조 검증, **GraphQL 보안, WebSocket 보안** 등 프로토콜 수준 API 요구.
- 왜 국내에 없는가: SR1-5(웹 서비스 요청 및 결과 검증)는 입력데이터 검증 관점의 항목으로 V1·V2 에 대응하며, GraphQL·WebSocket·HTTP 메시지 구조 같은 **프로토콜별 요구는 대응 항목이 없다**.
- ✅ 점검: API 스키마 기반 요청 검증, GraphQL 쿼리 깊이·복잡도 제한과 인트로스펙션 노출 여부, WebSocket 핸드셰이크의 인증·Origin 확인과 메시지 검증.

### 6.3 V9 Self-contained Tokens (7개 — L1 4 · L2 3 · L3 0)

- 섹션: 9.1 Token source and integrity · 9.2 Token content.
- 다루는 것: JWT 류 자기완결 토큰의 서명·무결성 검증과 내용(클레임) 검증 — 트리거 어휘 "JWT 검증"이 여기다.
- 왜 국내에 없는가: 국내 기준의 세션 관련 항목은 SR4-1(세션통제, 서버 세션 전제)이며, **자기완결 토큰이라는 형식 자체에 대한 검증 항목이 없다**.
- 7개 중 4개가 L1 — 규모는 작지만 최우선(L1) 비중이 높은 챕터다. L3 는 0개.
- ✅ 점검: 서명 알고리즘 허용 목록 운영(`none` 류 거부), 만료·발급자·대상 클레임 검증, 서명 검증을 라이브러리 기본 동작에 암묵적으로 맡기지 않는지, 토큰 무결성 검증 전 내용 사용 여부.

### 6.4 V10 OAuth and OIDC (36개 — L1 5 · L2 24 · L3 7)

- 섹션: 10.1 Generic OAuth/OIDC · 10.2 OAuth Client · 10.3 OAuth Resource Server · 10.4 OAuth Authorization Server · 10.5 OIDC Client · 10.6 OpenID Provider · 10.7 Consent Management.
- 다루는 것: **OAuth · OIDC** 기반 위임 인가·연합 인증의 역할별(클라이언트/리소스 서버/인가 서버/프로바이더) 요구.
- 왜 국내에 없는가: SR2-1~SR2-3 은 자체 인증(인증 대상·방식, 시도 제한, 비밀번호)의 설계 기준이며, **제3자 위임 인가 프로토콜의 역할별 보안 요구는 다루지 않는다**.
- **공백 7개 중 최대 규모(36개)** — 소셜 로그인·API 인가를 쓰는 서비스에서 실질 효용이 가장 큰 영역이다.
- ✅ 점검: 인가 코드 흐름 + PKCE 사용 여부, redirect_uri 의 사전 등록·정확 일치 검증, state·nonce 활용, 액세스 토큰의 저장 위치·수명, 리소스 서버의 토큰 검증(발급자·대상) 수행 여부.

### 6.5 V13 Configuration (21개 — L1 1 · L2 12 · L3 8)

- 섹션: 13.1 Configuration Documentation · 13.2 Backend Communication Configuration · 13.3 Secret Management · 13.4 Unintended Information Leakage.
- 다루는 것: 백엔드 간 통신 구성, **시크릿 관리**, 의도치 않은 정보 누출 등 구성(설정) 보안.
- 왜 국내에 없는가: 설계단계 20개에 구성 관리 유형이 없다. 구현단계 49개의 인접 항목(23번 하드코드된 중요정보 등, `secure-coding-kr` §6)이 일부 겹치지만, 설계단계 대응은 전무하다 — 구현단계 항목에 해당하면 국내 기준이 우선한다.
- ✅ 점검: 시크릿의 코드·저장소 하드코딩 여부(해당 시 📕 구현단계 23번으로 라우팅), 백엔드 간 통신의 인증·암호화 구성, 에러 응답·서버 헤더·디버그 엔드포인트의 정보 누출.

### 6.6 V15 Secure Coding and Architecture (21개 — L1 3 · L2 10 · L3 8)

- 섹션: 15.1 Documentation · 15.2 Security Architecture and Dependencies · 15.3 Defensive Coding · 15.4 Safe Concurrency.
- 다루는 것: 보안 아키텍처 문서화, **의존성(공급망) 관리** — 트리거 어휘 "SBOM" 류 논의가 이 영역이다 —, 방어적 코딩, 동시성 안전.
- 왜 국내에 없는가: 4.0.3 V1 Architecture 삭제 후 살아남은 아키텍처·의존성 요구가 모인 챕터로, 국내 20개 기준에는 아키텍처·의존성 유형이 없다. `secure-coding-kr` §10 의 **A03(공급망 실패) 국내 공백과 같은 맥락**이다.
- ✅ 점검: 의존성 목록의 파악 가능성과 알려진 취약점 점검 체계(의존성 매니페스트 관리), 위험한 언어 기능·역직렬화의 방어적 처리, 공유 자원 접근의 동시성 안전.

### 6.7 V17 WebRTC (12개 — L1 0 · L2 7 · L3 5)

- 섹션: 17.1 TURN Server · 17.2 Media · 17.3 Signaling.
- 다루는 것: 실시간 미디어 통신(WebRTC)의 TURN 서버·미디어·시그널링 보안.
- 왜 국내에 없는가: 실시간 미디어라는 도메인 자체가 국내 20개 기준에 없다. **L1 이 0개**인 특화 챕터 — WebRTC 를 쓰지 않는 앱에는 해당 없음(N/A)으로 정리하면 된다.
- ✅ 점검: TURN 서버 자격증명의 발급·수명 관리, 미디어 스트림 암호화 구성, 시그널링 채널의 인증·전송 보호.

### 6.8 지적 서술 템플릿

```

- 성격: 국제 모범사례 권고 — 구속력 없음. 국내 설계단계 20개 기준(2021.11)에는
  대응 항목이 없어 해당 문서를 근거로는 지적 불가(미기재 ≠ 부적합).
```

## 7. 국내 기준과 상충하는 항목 ⭐ — 비밀번호 정책

⚠️ **V6 Authentication 은 공백 챕터가 아니다** — 국내 SR2-1~SR2-3 에 대응한다. 문제는 공백이 아니라 **정면 충돌**이다. 공백 영역(§6)은 "국내 기준이 침묵"하지만, 이 절의 항목은 **양쪽 문서가 서로 반대 방향을 요구**한다.

### 7.1 V6.2.5 — 조합 규칙 금지 (L1)

📋 원문 (ASVS 5.0.0 영문판, 충돌 항목이므로 원문 인용):

> "Verify that passwords of any composition can be used, without rules limiting the type of characters permitted. There must be no requirement for a minimum number of upper or lower case characters, numbers, or special characters."

- ASVS 는 **문자 종류 조합 요구 자체를 금지**한다(대문자·소문자·숫자·특수문자 최소 개수 요구 불가).
- 국내 관행(8~9자리 + 문자종류 조합 강제)과 **정면 충돌**한다.

### 7.2 관련 요구사항 (V6.2 비밀번호 보안 섹션)

### 7.3 오판 시나리오

- ❌ **시나리오 A (국제 기준 과잉 적용)**: 점검자가 ASVS V6.2.5 를 근거로 "문자종류 조합 규칙을 제거하라"는 조치를 권고한다. → 오판이다. ASVS 는 구속력 없는 국제 권고이며, 국내 검증·진단 체계와 발주기관 정책은 조합 규칙을 요구할 수 있다. 조치를 따르면 **국내 기준 쪽에서 부적합 판정**을 받을 수 있다.
- ❌ **시나리오 B (근거 구분 없는 혼합 인용)**: 한 보고서 항목 안에서 국내 기준 26번(취약한 비밀번호 허용)과 V6.2.5 를 근거 구분 없이 병기한다. → 독자가 어느 쪽이 제도 판정 근거인지 구분할 수 없고, 두 문서의 요구 방향이 반대라 보완조치가 어느 쪽으로도 확정되지 않는다.
- ❌ **시나리오 C (반쪽 인용)**: "ASVS 도 최소 8자를 요구한다"(V6.2.1)만 인용해 국내 관행과 정합적인 것처럼 서술하고, 같은 섹션의 V6.2.5(조합 규칙 금지)·V6.2.10(정기 변경 강제 금지)은 언급하지 않는다. → 선택 인용이다. 같은 섹션 안에 충돌 항목이 있음을 밝혀야 한다.
- ✅ **올바른 서술**: "비밀번호 정책 — 제도 판정 근거: 국내 기준(진단가이드 26번 등)·발주기관 정책. 참고: OWASP ASVS 5.0.0 V6.2.5(영문판, 2026-09-17 조회, **구속력 없음**)는 조합 규칙 자체를 금지하며 국내 관행과 방향이 반대다."

### 7.4 판정 규칙 — 못박기

- 📕 **제도 판정은 국내 기준을 따른다.** 국내 검증·진단 맥락(진단가이드 26번 취약한 비밀번호 허용, `mobile-app-verify` FV-4.7 등)에서는 국내 기준·발주기관 정책이 판정 근거다. ASVS V6.2.5 를 근거로 "조합 규칙을 제거하라"고 조치하면 **국내 기준 위반으로 부적합 판정을 받을 수 있다.**
- 📋 ASVS 측 서술은 항상 **"구속력 없는 국제 권고"** 로 병기한다. 예: "참고: ASVS 5.0.0 V6.2.5(2026-09-17 조회, 구속력 없음)는 조합 규칙 자체를 금지하나, 제도 판정은 국내 기준을 따른다."
- ✅ 충돌하지 않는 항목(V6.2.4·V6.2.12 차단목록 대조, V6.2.9 긴 비밀번호 허용 등)은 국내 기준을 위반하지 않으면서 보강 적용할 수 있다 — 이 경우에도 출처·구속력 없음 병기는 동일하다.
- 이 두 문서를 한 보고서에서 함께 인용할 때는 항목마다 근거 문서를 명시하라 — `owasp-masvs` §2 의 방향 반대 항목(FV-5.1 ↔ MASWE-0051) 경고와 같은 원칙이다.
