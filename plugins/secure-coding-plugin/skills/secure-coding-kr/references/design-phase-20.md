# 제1유형. 입력데이터 검증 및 표현 (SR1-1 ~ SR1-10, p.35, p.43~102, p.506~508)

## SR1-1. DBMS 조회 및 결과 검증

- **설명**: SQL 질의문 내 입력값과 조회결과의 유효성 검증방법(필터링 등)을 설계하고, 유효하지 않은 값의 처리방법을 설계 (p.35).
- **세부 요구사항 / 설계 시 적용 방법** (부록 제1절, p.506~508):
  ① DB 연결 시 **최소권한 계정** 사용 ② 외부입력값이 삽입되는 **SQL 동적 생성·실행 금지** ③ 불가피한 동적 SQL은 **입력값 검증 후 사용**.
- **연관 구현단계 보안약점** (p.38): SQL 삽입 (#1).

## SR1-2. XML 조회 및 결과 검증

- **설명**: XPath/XQuery 등 질의문 내 입력값·조회결과의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① XML 쿼리 파라미터는 조작 불가하도록 **필터링하거나 자료형별 바인딩** 사용 (p.506~508).
- **연관 구현단계 보안약점** (p.38): XML 삽입 (#9), 부적절한 XML 외부개체 참조 (#8).

## SR1-3. 디렉토리 서비스 조회 및 결과 검증

- **설명**: LDAP 등 디렉토리 서비스 조회 시 입력값·결과의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① LDAP 인증 요청에 사용되는 외부입력값은 **LDAP 삽입 취약점이 없도록 필터링** (p.506~508).
- **연관 구현단계 보안약점** (p.38): LDAP 삽입 (#10).

## SR1-4. 시스템 자원 접근 및 명령어 수행 입력값 검증

- **설명**: 시스템 자원접근·명령어 수행 시 입력값의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① 외부입력값으로 시스템자원(IP, PORT, 프로세스, 메모리, 파일 등) 식별 시 **허가되지 않은 자원 사용 차단** ② 쉘 생성·명령어 실행 시 **악의적 명령어 실행 차단** (p.506~508).
- **연관 구현단계 보안약점** (p.38): 코드 삽입 (#2), 경로 조작 및 자원 삽입 (#3), 서버사이드 요청 위조 (#12), 운영체제 명령어 삽입 (#5).

## SR1-5. 웹 서비스 요청 및 결과 검증

- **설명**: 웹 서비스 요청(스크립트 게시 등)·응답결과의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① 입력값을 동적 응답페이지에 사용 시 **XSS 필터링** ② DB조회결과를 동적 응답페이지에 사용 시 **HTML 인코딩 또는 XSS 필터링** (p.506~508).
- **연관 구현단계 보안약점** (p.38): 크로스사이트 스크립트 (#4).

## SR1-6. 웹 기반 중요 기능 수행 요청 유효성 검증

- **설명**: 비밀번호 변경·결제 등 권한 확인이 필요한 중요기능 요청의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① **모든 요청에 대해 정상 사용자의 유효한 요청인지 판별 가능**하게 설계 (p.506~508).
- **연관 구현단계 보안약점** (p.38): 크로스사이트 요청 위조 (#11).

## SR1-7. HTTP 프로토콜 유효성 검증

- **설명**: 비정상 HTTP 헤더, 자동연결 URL 링크 등 HTTP 헤더·응답결과의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① 외부입력값을 쿠키·HTTP 헤더로 사용 시 **HTTP 응답분할 취약점이 없도록 필터링** ② 리다이렉트/포워드 URL로 사용 시 **허용된 URL 목록의 선택자로만 사용** (p.506~508).
- **연관 구현단계 보안약점** (p.38): 신뢰되지 않는 URL 주소로 자동접속 연결 (#7), HTTP 응답분할 (#13).

## SR1-8. 허용된 범위내 메모리 접근

- **설명**: 허용된 범위의 메모리 버퍼에만 읽기/쓰기 하도록 검증방법 및 범위초과 시 처리방법 설계 (p.35).
- **세부 요구사항**: ① C/C++ 등 메모리 직접관리 플랫폼은 **버퍼 경계값 검사 필수** ② **버퍼오버플로우 유발 취약 API 사용 통제** (p.506~508).
- **연관 구현단계 보안약점** (p.38): 포맷 스트링 삽입 (#17), 메모리 버퍼 오버플로우 (#16).

## SR1-9. 보안기능 입력값 검증

- **설명**: 보안기능(인증·권한부여 등) 입력값, 함수 외부입력값 및 수행결과의 유효성 검증방법 설계 (p.35).
- **세부 요구사항**: ① **사용자 역할·권한 결정 정보는 서버에서 관리** ② 쿠키·환경변수·파라미터 등 외부입력값이 보안기능 함수 인자로 사용될 때 **검증 후 제한적 사용** ③ **중요 상태정보·인증·권한결정 정보는 쿠키 전송 금지** (불가피 시 암호화) (p.506~508).
- **연관 구현단계 보안약점** (p.38): 보안기능 결정에 사용되는 부적절한 입력값 (#15), 정수형 오버플로우 (#14), Null Pointer 역참조 (#39).

## SR1-10. 업로드·다운로드 파일 검증

- **설명**: 업로드·다운로드 파일의 무결성·실행권한 등 유효성 검증방법 및 부적합 파일 처리방법 설계 (p.35).
- **세부 요구사항**: ① 업로드 파일의 **타입·크기·개수·실행권한 제한** ② **저장 파일이 외부에서 식별되지 않도록** ③ **다운로드 요청 파일명 검증** ④ 다운로드 받은 소스코드·실행파일 **무결성 검사** (p.506~508).
- **연관 구현단계 보안약점** (p.38): 위험한 형식 파일 업로드 (#6), 부적절한 전자서명 확인 (#27), 무결성 검사 없는 코드 다운로드 (#32).

# 제2유형. 보안기능 (SR2-1 ~ SR2-8, p.36, p.103~163, p.509~510)

## SR2-1. 인증 대상 및 방식

- **설명**: 중요정보·기능 특성에 따라 인증방식을 정의하고 우회 불가하게 설계 (p.36).
- **세부 요구사항**: ① 중요기능·리소스는 **인증 후 사용** 정책 적용 ② **인증우회·권한상승 방지** ③ 중요기능은 **2단계(2-factor) 인증 고려** (p.509~510).
- **연관 구현단계 보안약점** (p.38): 서버사이드 요청 위조 (#12), 적절한 인증 없는 중요기능 허용 (#18), 부적절한 인증서 유효성 검증 (#28), DNS lookup에 의존한 보안결정 (#48).

## SR2-2. 인증 수행 제한

- **설명**: 반복된 인증 시도를 제한하고 인증 실패 이력을 추적하도록 설계 (p.36).
- **세부 요구사항**: ① **인증시도 횟수 제한** 및 초과 시 인증제한 정책 ② **실패한 인증시도 로깅**으로 추적 가능 (p.509~510).
- **연관 구현단계 보안약점** (p.38): 반복된 인증시도 제한 기능 부재 (#33).

## SR2-3. 비밀번호 관리

- **설명**: 생성규칙·저장방법·변경주기 등 비밀번호 관리정책별 안전한 적용방법 설계 (p.36).
- **세부 요구사항**: ① KISA 『암호이용안내서』의 **비밀번호 생성규칙** 적용 ② 네트워크 전송 시 **암호화 또는 암호화 채널** ③ 저장 시 **솔트가 적용된 안전한 해쉬함수**, 해쉬 실행은 **서버에서** ④ **재설정/변경 규칙** 정의 ⑤ **비밀번호 관리 규칙** 정의 (p.509~510).
- **연관 구현단계 보안약점** (p.38): 하드코드된 중요정보 (#23), 취약한 비밀번호 허용 (#26).
- > 💡 현행 권고: 저장용 해시는 Argon2id·bcrypt·scrypt·PBKDF2 등 키 스트레칭 함수 사용이 현행 표준 (출처: OWASP Password Storage Cheat Sheet, NIST SP 800-63B). 기준 항목은 원문 그대로 유지.

## SR2-4. 중요자원 접근통제

- **설명**: 중요자원 정의 및 신뢰할 수 있는 접근통제 방법(권한관리 포함) 설계, 실패 시 처리방법 설계 (p.36).
- **세부 요구사항**: ① **중요자원 접근통제 정책** ② **중요기능 접근통제 정책** ③ **관리자 페이지 접근통제 정책** (p.509~510).
- **연관 구현단계 보안약점** (p.38): 부적절한 인가 (#19), 중요한 자원에 대한 잘못된 권한 설정 (#20).

## SR2-5. 암호키 관리

- **설명**: 암호키 생성·분배·접근·파기 등 생명주기별 관리방법을 안전하게 설계 (p.36).
- **세부 요구사항**: ① DB데이터 암호화 키는 KISA 「암호이용안내서」 방법 적용 ② 설정파일(xml, Properties) 내 중요정보 암호화 키는 **암호화하여 별도 디렉터리 보관** (p.509~510).
- **연관 구현단계 보안약점** (p.38): 하드코드된 중요정보 (#23), 주석문 안에 포함된 시스템 주요정보 (#30).

## SR2-6. 암호연산

- **설명**: 국제표준·검증필 암호모듈의 안전한 알고리즘 선정, 충분한 키 길이·솔트·난수 적용 설계 (p.36).
- **세부 요구사항**: ① KISA 『암호이용안내서』의 **알고리즘·키 길이** 사용 ② 해쉬 사용 시 **안전한 해쉬 알고리즘 + 솔트** ③ **안전한 난수 생성 알고리즘** 사용 (p.509~510).
- **연관 구현단계 보안약점** (p.38): 취약한 암호화 알고리즘 사용 (#21), 충분하지 않은 키 길이 사용 (#24), 적절하지 않은 난수 값 사용 (#25), 부적절한 인증서 유효성 검증 (#28), 솔트 없이 일방향 해쉬 함수 사용 (#31).
- ※ 알고리즘·키 길이의 적합성 판정은 `crypto-policy-kr` 스킬 참조.

## SR2-7. 중요정보 저장

- **설명**: 중요정보(비밀번호, 개인정보 등)의 저장·보관 방법이 안전하도록 설계 (p.36).
- **세부 요구사항**: ① 중요정보·개인정보 **암호화 저장** ② **불필요한 중요정보가 메모리에 남지 않도록** (p.509~510).
- **연관 구현단계 보안약점** (p.38): 암호화되지 않은 중요정보 (#22), 사용자 하드디스크에 저장되는 쿠키를 통한 정보 노출 (#29).

## SR2-8. 중요정보 전송

- **설명**: 중요정보(비밀번호, 개인정보, 쿠키 등)의 전송 방법이 안전하도록 설계 (p.36).
- **세부 요구사항**: ① 인증정보 등 **민감정보 전송 시 암호화** ② **쿠키 포함 중요정보 암호화 전송** (p.509~510).
- **연관 구현단계 보안약점** (p.38): 암호화되지 않은 중요정보 (#22).

# 제3유형. 에러처리 (SR3-1, p.36, p.164~170, p.511)

## SR3-1. 예외처리

- **설명**: 오류메시지에 중요정보(개인정보·시스템 정보·민감 정보)가 노출되거나 부적절한 에러·오류 처리로 의도치 않은 상황이 발생하지 않도록 설계 (p.36).
- **세부 요구사항**: ① **명시적 예외는 예외처리 블럭**으로 처리 기능 구현 ② **런타임 예외는 입력값 범위 체크**로 정상 동작 값만 사용 보장 ③ 에러 발생 시 **상세 에러 정보 사용자 노출 금지** (p.511).
- **연관 구현단계 보안약점** (p.38): 오류 메시지 정보노출 (#36).

# 제4유형. 세션통제 (SR4-1, p.37, p.171~178, p.511)

## SR4-1. 세션통제

- **설명**: 다른 세션 간 데이터 공유금지, 세션ID 노출금지, (재)로그인 시 기존 세션ID 재사용금지 등 안전한 세션 관리방안 설계 (p.37).
- **세부 요구사항**: ① **세션간 데이터 공유 금지** 설계 ② **세션의 안전한 관리** ③ **세션ID의 안전한 관리** (p.511).
- **연관 구현단계 보안약점** (p.38): 잘못된 세션에 의한 데이터 정보 노출 (#44).

# 분석·설계단계 진단절차 상세 (p.20~27)

- 진단 시점: "설계가 완료되고 구현이 시작되거나 구현을 준비하는 시점에 진단하는 것이 적절하다." (p.20)
- 진단 대상: "분석과 설계 과정에서 만들어진 설계 산출물" (p.20). 한국정보화진흥원 "CBD SW개발 표준 산출물 가이드"의 산출물 종류·이름을 기반으로 한다 (p.20, p.25).
- 절차: **착수 → 진단 → 보고서 작성 및 제출 → 종료** (p.21).

## 가. 착수단계 (p.22)

1. **착수 회의 실시** — 진단원·발주자·사업자 참석. 진단원이 분석·설계단계 진단의 목적, 적용기준과 진단항목, 일정 등 전반적 절차·내용을 설명하고 필요한 산출물을 요청.

## 나. 진단단계 (p.22~23)

1. **산출물 접수** — 개발사가 분석·설계 산출물을 제공. 진단원은 제출 목록을 확인하고 누락·추가자료 필요 시 요청.
2. **산출물 검토** — SW개발보안 가이드의 분석·설계단계 SW보안강화 활동에 명시된 보안활동과 **보안설계 기준**을 기반으로 세부 내용 검토, **보안설계 항목 식별** 및 **보안 대책의 적절한 수립 여부** 확인.
3. **보안약점 진단 및 개선방안 도출** — 기준 충족 여부 확인, 개선 필요사항 발견 시 구체적 개선방안 도출. 가이드·관련 법률 등 **객관적 근거** 필요, **현실적으로 실행 가능한 수준**으로.
4. **공동리뷰** — 발주사·개발사 담당자 인터뷰로 진단현황·주요 문제점 설명, 미파악 사항 의견 청취, 개선방안 실행 가능성 확인.
5. **개선방안 확정** — 설계항목별 일관성 유지, 증적 자료(분석·설계 산출물 등) 기반 도출, 공동리뷰 결과 반영.

## 다. 보고서 작성 및 제출 단계 (p.23~24)

1. **보고서 초안 작성** — 보안약점 판단 사유·증적 자료 명시, 논리적 일관성 유지. 보고서 필수 기재: **보안설계 기준에 따른 진단 결과, 진단원, 진단 기간, 진단 대상 범위(분석·설계 산출물 등), 개선방안**.
2. **공동리뷰** — 사실 여부 검토, 추가 증적 제출 의사, 개선 여부·개선일정 검토. 증적 누락·잘못된 보안약점 도출·실현 가능성 낮은 개선방안 등 수정사항 확인·반영.
3. **보고서 제출** — 수정 근거·자료 추가 검토 후 **최종진단결과보고서** 작성, 발주사 제출.

## 라. 종료단계 (p.24)

1. **종료회의 실시** — 최종 검토 결과 설명, 질의응답으로 공감대 형성. 개선사항이 있으면 **기한을 정해 수정·증적 제출 요청**, 개선 완료 여부를 검토·확인하여 추후 보고서에 추가.
