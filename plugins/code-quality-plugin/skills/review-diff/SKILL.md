# review-diff — 리뷰 보고 형식

## 입력

- 범위: `git diff <base>..<head>` 또는 작업 트리 diff, 관련 계획·스펙 절(경로·절 번호)
- 재리뷰면 이전 리뷰 파일 경로

## 절차

1. 계획·스펙의 해당 절과 diff 를 읽는다. 지적마다 코드를 직접 읽거나 짧은 재현(명령·수치)으로 근거를 만든다
2. 테스트가 바뀐 동작을 실제로 단언하는지 확인한다 — 구현을 그대로 따라 쓴 단언, 항상 통과하는 단언은 지적.
   변이 결과(JSON 등)가 주어지면 살아남은 변이를 나열한다
3. 재리뷰면 이전 지적마다 `반영` · `미반영` · `철회(사유)` 를 표시한다

## 보고 형식 (이 순서·제목 고정)

```markdown
## 판정: GO | GO-with-fixes | BLOCK
- 근거 한 줄(High 수·막는 이유)

## 지적
| # | 심각도 | 위치 | 문제 | 근거 | 제안 |
|---|---|---|---|---|---|
| 1 | High | `path/file.py:42` | 무엇이 틀리는가(조용히 틀리는 경로면 명시) | 재현 명령·수치 또는 읽은 코드 | 한 줄 |

## 테스트 단언 점검
- 단언이 약한 테스트 · 살아남은 변이(있으면)

## 재리뷰 대조 (재리뷰일 때만)
| 이전 # | 상태 | 비고 |

## 검증하지 못한 것
- 실행하지 못한 게이트·읽지 못한 파일 — 없으면 "없음"
```

- 심각도: **High** = 잘못된 결과가 오류 없이 통과하거나 데이터 손실·보안 문제 · **Medium** = 특정 조건에서 틀리거나 유지보수 위험 ·
  **Low** = 표현·중복·사소한 개선
- 판정: High 1건 이상 → BLOCK(고치기 전 진행 불가) 또는 GO-with-fixes(수정이 국소적일 때), High 0건 → GO
- 상세가 길면 `reviews/<id>.md`(또는 요청이 지정한 경로)에 쓰고, 메시지에는 판정·High 목록·파일 경로만 보낸다
- 리뷰어는 소스를 고치지 않는다
