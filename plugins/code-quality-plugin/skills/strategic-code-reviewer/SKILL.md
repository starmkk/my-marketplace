# Strategic Code Reviewer

구조 품질을 6원칙으로 판단한다. 목적은 지적 목록을 늘리는 게 아니라 **바꿀 가치가 있는 것만 골라내는 것**이다.
원칙은 규칙이 아니라 렌즈다. 렌즈를 통해 본 것이 전부 결함은 아니다.

## 0. 두 가지 모드 — 먼저 어느 쪽인지 판단

| 모드 | 진입 신호 | 산출물 |
|---|---|---|
| **설계 협의** (작성 전) | 새 함수/클래스/모듈을 만들려 함, "어디에 둘까", "이렇게 짜려는데" | 배치·분해·재사용 판단 + 승인/수정안 |
| **구현 리뷰** (작성 후) | 코드가 이미 있음, "리뷰해줘", diff 존재 | 우선순위 붙은 개선안 |

설계 협의가 훨씬 저렴하다. 잘못된 구조로 300줄을 쓴 뒤 되돌리는 비용이 크기 때문에, 작성 전 신호가 조금이라도 보이면 협의 모드로 먼저 들어가라.

---

## 1. 설계 협의 모드

구현 코드를 대신 써 주는 자리가 아니다. **결정 4개만 내리고 넘긴다.**

1. **이미 있는가** — 같은 일을 하는 코드가 저장소에 있는지 먼저 찾는다. 심볼 검색(Serena `find_symbol`)이나 grep으로 확인하지 않은 채 "없을 것"이라고 넘기지 말 것. 있으면 신규 작성 자체가 취소된다.
2. **정말 필요한가 (YAGNI)** — 지금 요구에 필요한가, 아니면 "나중에 쓸 것 같아서"인가. 후자면 지금은 만들지 않는다.
3. **어디에 두는가 (SoC)** — 이 저장소의 배치 규약을 따른다. 진입점은 최상위, 재사용 로직은 도메인 하위, 순수 함수와 I/O는 분리.
4. **어떻게 쪼개는가 (SRP)** — 한 함수가 "그리고"로 이어지는 설명을 요구하면 이미 둘이다. 다만 처음부터 3개로 쪼개는 것도 과설계다. 2개로 시작해도 된다.

출력은 짧게. 승인이면 "이대로 진행" 한 줄이면 충분하고, 수정이 필요하면 무엇을 왜 바꾸는지만 적는다.

---

## 2. 구현 리뷰 모드 — 절차

1. **범위 확정** — 리뷰 대상이 diff인지 파일 전체인지 확정한다. `git diff`/`git diff --cached`/`git log -p -1` 중 맞는 것을 실제로 실행해 확인한다. 범위를 넓히면 "이 코드와 무관한 기존 문제"까지 섞여 신호가 흐려진다.
2. **컨텍스트 확보** — 리뷰 대상이 호출하는 쪽과 호출되는 쪽을 본다. 호출 지점을 모르면 "이 인자는 불필요하다" 같은 판단이 틀린다.
3. **6원칙 스캔** — §3의 렌즈를 순서대로 적용한다.
4. **오탐 제거** — §4의 "지적하지 말아야 할 때"로 각 후보를 거른다. 여기서 살아남지 못한 항목은 보고서에 넣지 않는다.
5. **우선순위 부여** — §5 기준으로 등급을 매긴다.
6. **보고** — §6 형식.

## 3. 여섯 개의 렌즈

### DRY — 지식의 중복인가, 코드의 유사성인가

찾을 것: 같은 **결정**이 여러 곳에 박혀 있는 경우. 상수·임계값·포맷 규칙·경로 조립·검증 로직이 복붙된 자리.

핵심 구분은 이것이다. **모양이 같은 코드와 이유가 같은 코드는 다르다.** 두 함수가 우연히 비슷하게 생겼지만 서로 다른 이유로 변하는 거라면, 합치는 순간 한쪽 요구가 바뀔 때마다 분기가 늘어난다. 잘못된 추상화는 중복보다 비싸다.

판정 질문: *요구사항이 바뀌면 이 두 곳을 반드시 같이 고쳐야 하는가?*
- 예 → 진짜 중복. 통합 대상.
- 아니오 → 우연한 유사성. 놔둔다.

### KISS — 읽는 사람의 부담

찾을 것: 중첩 3단 이상, 한 줄에 얽힌 삼항 연산, 되돌리기 어려운 영리한 트릭, 조건이 5개 이상인 분기 덩어리, 이름 없는 중간 계산.

단순함은 줄 수가 아니라 **이해에 필요한 단계 수**다. 5줄짜리 정규식 한 줄보다 15줄짜리 명시적 파싱이 단순할 수 있다. "짧게 줄이자"는 제안이 실제로는 읽기를 어렵게 만드는지 스스로 검토하라.

가드절로 조기 반환하기, 중간 계산에 이름 붙이기, 부울 표현식을 이름 있는 술어로 빼기 — 이 셋이 대부분의 복잡도를 걷어낸다.

### SRP — 변경 이유가 몇 개인가

찾을 것: "그리고"가 들어가는 함수 설명, I/O와 계산이 뒤섞인 함수, 파싱과 검증과 저장을 함께 하는 클래스, 인자 개수가 많고 그중 일부는 특정 분기에서만 쓰이는 시그니처.

판정 기준은 줄 수가 아니라 **변경 이유**다. 200줄이어도 하나의 이유로만 바뀌면 그대로 두고, 20줄이어도 두 이유로 바뀌면 쪼갠다.

이 저장소에서 특히 값진 분리는 **순수 함수 / I/O 경계**다. 계산이 순수하면 테스트가 mock 없이 성립하고, 그게 곧 검증 가능성이다.

### YAGNI — 지금 쓰이는가

찾을 것: 호출자가 없는 공개 함수, 항상 같은 값만 넘어오는 매개변수, 구현체가 하나뿐인 인터페이스, "확장 대비" 주석이 달린 훅, 쓰이지 않는 설정 항목.

호출자 없음은 grep이나 `find_referencing_symbols`로 **확인한 뒤** 말하라. 동적 호출·엔트리포인트·테스트 전용 API를 죽은 코드로 오판하기 쉽다.

미래 요구는 대체로 예상과 다르게 온다. 지금 없는 요구를 위해 만든 유연성은 대개 도착했을 때 맞지 않는다.

### SoC — 층이 섞였는가

찾을 것: 비즈니스 로직 안의 HTML/SQL 문자열, 도메인 함수 안의 `print`/로깅 포맷, 하위 계층이 상위 계층 타입을 아는 역방향 의존, 설정 파일 경로가 계산 로직 한복판에 하드코딩된 자리.

배치 규약이 있는 저장소라면 그 규약이 곧 관심사 경계다. 새 코드가 규약과 다른 자리에 놓였다면, 코드가 틀렸거나 규약이 낡은 것이다 — 어느 쪽인지 판단해서 말하라.

### Meaningful Naming — 이름이 거짓말하지 않는가

찾을 것: `data`, `tmp`, `result`, `handle`, `process`, `manager` 같은 무내용 이름. 실제 동작과 어긋난 이름(`get_`으로 시작하는데 상태를 바꾼다). 부정형 부울(`is_not_ready` → `is_ready`). 같은 개념에 다른 단어(한곳은 `transcript`, 한곳은 `record`). 축약(`cfg`, `ppl`)이 문맥 없이 쓰인 자리.

가장 나쁜 이름은 짧은 이름이 아니라 **틀린 이름**이다. 틀린 이름은 읽는 사람을 잘못된 방향으로 데려간다. 스코프가 좁으면 짧은 이름도 괜찮다(3줄짜리 루프의 `i`는 문제없다).

프로젝트 규약이 있으면 그것이 우선한다. 이 저장소는 언어별 케이스 규약과 상수 접두사 규약이 정해져 있으니 취향으로 뒤집지 말 것.

## 4. 지적하지 말아야 할 때 — 오탐 필터

리뷰의 신뢰는 **틀린 지적을 하지 않는 데서** 나온다. 다음에 해당하면 보고서에서 뺀다.

- **두 번밖에 안 나온 유사 코드** — 세 번째가 나오면 그때 합쳐도 늦지 않다. 두 번은 아직 패턴이 아니다.
- **테스트 코드의 반복** — 테스트는 각각이 독립적으로 읽혀야 한다. 셋업을 과하게 공유하면 실패 원인 추적이 어려워진다. 테스트의 중복은 대체로 미덕이다.
- **린터·포매터가 이미 강제하는 것** — 줄 길이, import 정렬, 따옴표 스타일. 도구가 통과시킨 것을 사람이 다시 말할 필요 없다.
- **프로젝트 규약대로 쓴 코드** — 개인 취향으로 규약을 뒤집지 않는다. 규약 자체가 문제라면 코드가 아니라 규약을 고치자고 말하라.
- **경계 지점의 의도된 중복** — 모듈 간 계약을 느슨하게 유지하려고 일부러 복제한 자리가 있다. 결합을 늘리는 통합은 개선이 아니다.
- **성능·정확성 때문에 복잡한 코드** — 이유가 주석에 있고 근거가 타당하면 단순화 대상이 아니다. 주석이 없다면 지적할 것은 복잡도가 아니라 **설명 부재**다.
- **근거를 확인하지 못한 추측** — "아마 안 쓰일 것", "느릴 것 같음"은 보고하지 않는다. 확인하고 말하거나, 확인이 필요하다는 사실 자체를 적는다.

## 5. 우선순위 — 무엇부터 고칠 가치가 있는가

| 등급 | 기준 | 예 |
|---|---|---|
| **높음** | 지금 버그를 부르거나, 앞으로 변경할 때 반드시 걸린다 | 같은 임계값이 3곳에 복붙됨, 함수 하나가 파싱+검증+저장을 다 함 |
| **중간** | 읽기·테스트를 방해하지만 당장 깨지진 않는다 | 중첩 4단, 순수 로직에 I/O가 섞임 |
| **낮음** | 다음에 그 파일을 만질 때 함께 정리하면 되는 것 | 지역 변수 이름, 주석 문구 |

높음이 없으면 없다고 명시하라. 억지로 등급을 채우면 진짜 신호가 묻힌다.

## 6. 보고 형식

```markdown
## 리뷰 범위
<대상 파일/커밋, 확인한 방법>

## 판정
<한 줄 요약 — 이대로 진행 가능 / 높음 N건 선반영 권장>

## 개선 항목
### [높음] <제목>
- 위치: `path/to/file.py:120`
- 원칙: SRP
- 현상: <무엇이 어떻게 되어 있는가 — 사실만>
- 이유: <왜 문제인가 — 어떤 변경에서 걸리는가>
- 제안: <구체적 수정 방향. 필요하면 3~5줄 코드>

## 확인 필요
<판단에 근거가 부족해 사용자 확인이 필요한 항목. 없으면 생략>
```

- 원칙 이름을 붙이되, **원칙 때문에 고치라고 하지 말라.** "DRY 위반이므로 통합"이 아니라 "임계값이 바뀌면 3곳을 모두 고쳐야 하고 하나를 빠뜨리면 판정이 어긋난다"가 이유다. 원칙은 분류 태그일 뿐이고, 설득은 결과로 한다.
- 위치는 `파일:줄` 로 적는다. 클릭해서 바로 갈 수 있어야 한다.
- 지적할 게 없으면 없다고 말하라. 깨끗한 코드를 깨끗하다고 말하는 것도 리뷰 결과다.

## 7. 검증 — 제안을 냈으면 깨지지 않는지 확인

리팩터링 제안을 **직접 적용했다면**, 그 저장소의 검증 명령을 실행해 통과를 확인한 뒤 보고하라. 구조 개선이 동작을 바꾸면 개선이 아니다. 프로젝트에 정의된 lint·타입체크·테스트 명령이 있으면 그것을 쓰고, 결과를 있는 그대로 적는다(통과하지 못했으면 통과하지 못했다고).

제안만 하고 적용하지 않았다면 검증은 구현하는 쪽의 몫이며, 보고서에 "적용 후 <명령> 확인 필요"로 남긴다.
