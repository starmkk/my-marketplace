# 제1절 입력데이터 검증 및 표현 (17개, p.180~313)

> 절 정의 (p.180): "프로그램 입력값에 대한 검증 누락 또는 부적절한 검증, 데이터의 잘못된 형식지정, 일관되지 않은 언어셋 사용 등으로 인해 발생되는 보안약점으로 SQL 삽입, 크로스사이트 스크립트(XSS) 등의 공격을 유발할 수 있다."

## 1. SQL 삽입 (CWE-89, p.180~193)

**정의 (p.180)**
- DB 연동 웹 응용프로그램에서 입력 데이터의 유효성 검증이 없으면 공격자가 입력 폼·URL 입력란에 SQL 문을 삽입하여 DB 정보를 열람·조작할 수 있다. 취약한 프로그램은 입력값을 필터링 없이 받아 **동적쿼리(Dynamic Query)**를 생성하므로 의도하지 않은 쿼리가 실행된다.
- (부록 p.512) "SQL 질의문을 생성할 때 검증되지 않은 외부 입력 값을 허용하여 악의적인 질의문이 실행가능한 보안약점".

**대응방안 (p.180)**
- `PreparedStatement` 객체 등으로 DB에 **컴파일된 쿼리문(상수)** 전달.
- PreparedStatement를 쓰더라도 외부입력값의 **특수문자·쿼리 예약어 필터링**.
- Struts/Spring 등 프레임워크의 **외부입력값 검증모듈·보안모듈** 활용.

**진단방법 (p.186, p.188~192)**
- ① `Statement` 객체로 쿼리가 실행되는 부분 확인 → ② `PreparedStatement` 여부 확인 → ③ PreparedStatement + `setString` 등 바인딩이면 기본 안전, 단 외부 입력값이면 필터링 모듈 존재를 추가 확인.
- 하위 유형별 취약 판정: **JDO**(`pm.newQuery()` 문자열 연결), **J2EE Persistence**(`em.createNativeQuery()` 문자열 연결), **MyBatis Data Map**(`$name$` 문자열 치환), **Hibernate**(`session.createQuery()` 문자열 연결).

**코드예제 (p.181~185)** — JDBC(Java), MyBatis, Hibernate, C#
- 핵심 차이: 문자열 결합 동적 쿼리 → **바인딩 변수(`?`, `:name`, MyBatis `#{}`, C# `@param`)** 사용. MyBatis는 `${}` → `#{}`.

**오탐 주의사항 (p.192)**
- Hibernate에서 `createQuery("… = ?")` + `query.setString(0, name)` 또는 `"… = :name"` + `query.setParameter("name", name)` 형태의 **파라미터 바인딩은 취약하지 않다**.

## 2. 코드 삽입 (CWE-94, CWE-95, p.194~200)

**정의 (p.194)**
- 공격자가 SW의 의도된 동작을 변경하도록 **임의 코드를 삽입**하는 보안약점. OS 명령어 삽입과 달리 "프로그래밍 언어 자체의 기능에 의해서만 제한된다". 권한 탈취·인증 우회·시스템 명령어 실행 가능.

**대응방안 (p.194)**
- **동적코드 실행 함수를 사용하지 않는다.** 필요 시 외부 입력값을 **화이트리스트 방식**으로 제한하거나 유효한 문자만 허용하도록 **필터링**한다.

**진단방법 (p.196~199)**
- ① 언어별 **동적실행 함수** 확인 (Java `ScriptEngine.eval`, JS `new Function()`, PHP `eval()` 등) → ② 실행 데이터가 신뢰 가능한지 확인. 검증절차가 없으면 취약.
- PHP 삽입코드 예: `/vul.php?arg=1;phpinfo()`, `1;system("cat /etc/passwd")` (p.197). `include($MessageFile)`처럼 사용자 입력이 파일에 기록되고 파싱·실행되는 경우도 취약 (p.198).

**코드예제 (p.194~196)** — JAVA, JSP
- 핵심 차이: 외부 입력 `src`를 `scriptEngine.eval(src)`로 즉시 실행 → **정규식(`[\\w]*`) 검증 후 실행 또는 화이트리스트 매칭 시에만 정해진 메소드 호출**.

**오탐 주의사항 (p.198~199)**
- `preg_replace`로 **위험 기호 제거 후** `eval()` 사용 시 안전. 외부 입력값을 사용 전 검증(`Filter.filterScript()` 등)하면 안전. **동적 실행함수가 있어도 외부 입력값을 실행하지 않으면** 안전.

## 3. 경로 조작 및 자원 삽입 (CWE-99, CWE-22, p.201~210)

**정의 (p.201)**
- 검증되지 않은 외부입력값으로 파일·서버 등 **시스템 자원 접근·식별**을 허용하면 입력값 조작으로 보호 자원에 임의 접근 가능. 자원 수정·삭제, 정보누출, 자원 충돌로 인한 서비스 장애 유발.

**대응방안 (p.201)**
- 외부 입력을 자원(파일·소켓 포트 등) 식별자로 쓸 때 **적절한 검증** 또는 **사전 정의 리스트에서 선택**. 파일명인 경우 **경로 순회 문자(`/ \ ..`) 제거 필터** 적용.

**진단방법 (p.206)**
- 경로 생성·자원제어 코드에 외부 입력값이 직접 영향을 주는지, 필터링·리스트 선택이 있는지 확인. 시스템 경로는 **시스템 함수 호출로 생성**하는 것이 바람직.
- [경로 조작] 파일객체 사용 확인 → 외부 직접 접근 확인. 경로 순회 문자 제거 없으면 취약. [자원 삽입] 매핑표·리스트를 가지면 안전, 그 외 취약.
- 경로순회 문자를 필터링해도 **컨텍스트 경로 접근이 가능**하면(웹·서블릿 설정파일 접근) 취약 (p.206).

**코드예제 (p.202~205)** — JAVA, C#, C
- 핵심 차이: 외부 입력 파일명을 그대로 사용 → **경로순회 문자열 검사·제거 후 사용**.

**오탐 주의사항 (p.208~210)**
- `getRealPath()`, `getContextPath()` 등 **내장함수 값은 안전**. 프레임워크의 **시스템 프로퍼티** 사용은 오탐 처리, 단 **개별 사용 프로퍼티는 정탐**.

## 4. 크로스사이트 스크립트 (XSS) (CWE-79, p.211~222)

**정의 (p.211)**
- 웹 페이지에 악의적인 스크립트를 포함시켜 사용자 측에서 실행되게 유도. 검증되지 않은 외부 입력이 동적 웹페이지 생성에 사용되면 열람자 권한으로 부적절한 스크립트가 수행되어 정보유출 등을 유발.

**대응방안 (p.211)**
- `< > & "` 를 `&lt; &gt; &amp; &quot;`로 **치환**. HTML 태그 허용 게시판은 **화이트리스트 태그만 허용**.
- 방법1 문자열 치환, 방법2 JSTL `<c:out>`, 방법3 검증된 라이브러리(NAVER Lucy-XSS-Filter, OWASP ESAPI 등), C#은 AntiXss.

> 💡 현행 권고: 단순 문자 치환보다 **출력 컨텍스트(HTML body / attribute / JS / URL)별 인코딩**이 우선이다 (출처: OWASP Cross Site Scripting Prevention Cheat Sheet). 기준 항목·판정 방식은 원문 그대로 따른다.

**진단방법 (p.215~222)**
- ① 웹 페이지 출력 변수 확인 → ② 외부 입력값 또는 DB 저장값 여부 확인 → 적절한 필터·프레임워크 검증 존재 시 안전, 그 외 취약.
- 유형별: **Reflected**(요청값 즉시 출력), **Stored**(DB 저장 후 출력), **DOM**(`document.write()` 인자).
- 취약 판정 사례: `<c:out escapeXml="false">`; `<script>`만 공백 치환(`<sc<script>ript>` 우회); HTML 주석 안 입력도 `-->` 로 주석 닫고 공격 가능 (p.216~217).

**코드예제 (p.212~215)** — JAVA, C#, C
- 핵심 차이: 검증 없이 응답 페이지 출력 → **위험 문자열 치환 / `c:out` / XSS 필터 라이브러리 경유 출력**.

**오탐 주의사항 (p.217~219)**
- 공격 문자열이 **URL로 포함되어 이동**만 하는 경우 / `<c:out>`·`escapeXml` 사용 / **출력값이 숫자형** / `subString` 길이 제한 / **내부 고정값** / **System 콘솔 출력** / **사용자 입력값이 아닌 경우** 모두 안전.
- Stored XSS: 메뉴명 등 **사용자 입력으로 수정되지 않는 DB 값** 출력은 취약하지 않음. 단 "사용자 입력으로 수정되는 변수인지는 정적도구로 판단하기 어렵다" (p.219).

## 5. 운영체제 명령어 삽입 (CWE-78, p.223~231)

**정의 (p.223)**
- 검증 없는 사용자 입력값이 **운영체제 명령어의 일부 또는 전부**로 실행되어 의도하지 않은 시스템 명령어 실행, 권한 변경, 시스템 운영 악영향.

**대응방안 (p.223)**
- 웹 인터페이스로 시스템 명령어를 전달시키지 않는 구성. 외부 값을 **검증 없이 내부 명령어로 사용 금지**. 필요 시 **명령어 후보를 미리 지정하고 외부 입력으로 선택**만 하게 한다.

**진단방법 (p.227~231)**
- ① 명령어 실행 함수(`exec()`, `system()`, `Runtime.getRuntime().exec` 등) 호출 확인 → ② 외부 값이 명령어 일부/전부로 사용되는지 확인. **화이트리스트 선택값 또는 적절한 검증이면 안전**, 그 외 취약.

**코드예제 (p.223~227)** — JAVA, C#, C
- 핵심 차이: 외부 입력으로 실행 프로그램 무제한 지정 → **화이트리스트 제한(노트패드/계산기 등) 또는 정규식 검증·우회문자 필터링 후 사용**.

**오탐 주의사항 (p.230~231)**
- **시스템 프로퍼티 사용은 안전**, **개별 사용 프로퍼티는 취약** 판정. 사용자 입력값이 명령어 실행에 들어가지 않으면 안전. `srcFile.getName()`처럼 **file separator·`..` 포함 불가 값**은 안전.

## 6. 위험한 형식 파일 업로드 (CWE-434, p.232~238)

**정의 (p.232)**
- 서버 측 실행 가능 **스크립트 파일(asp, jsp, php 등)이 업로드 가능**하고 웹으로 직접 실행될 수 있으면, 시스템 내부명령어 실행·외부 연결로 시스템 제어 가능.

**대응방안 (p.232)**
- **화이트리스트 확장자만 허용**. 저장 시 **파일명·확장자를 추측 불가 문자열로 변경**. 저장 경로는 **web document root 밖**. 가능하면 **실행 속성 제거**.

**진단방법 (p.235~238)**
- ① 외부 입력에서 파일명을 얻는 부분 확인 → ② **허용 확장자만 업로드 허용**하는지 확인. 허용 파일 제한 또는 파일명 변경 저장이면 안전, 그 외 취약.
- `getOriginalFilename()` 사용 + 확장자 미체크 → 취약. 확장자 체크가 **대소문자 구분 없이** 이뤄지지 않으면(`JSP, Jsp, PHP` 등 통과) 취약 (p.236).

**코드예제 (p.232~235)** — JAVA, C#
- 핵심 차이: 파일명 무검증 사용 → **마지막 `.` 기준 실제 확장자를 대소문자 무시 화이트리스트로 확인, 타입·크기 제한**.

**오탐 주의사항 (p.237~238)**
- 확장자 체크·필터링이 있으면 안전. `getOriginalFilename()` **리턴값을 저장하여 사용하지 않으면** 취약하지 않다고 판정.

## 7. 신뢰되지 않는 URL 주소로 자동접속 연결 (CWE-601, p.239~243)

**정의 (p.239)**
- 사용자 입력값을 **외부사이트 주소로 사용해 자동 연결**하는 서버 프로그램은 **피싱(Phishing)** 공격에 노출. 공격자는 폼 요청을 변조하여 사용자를 위험한 URL로 접속시킬 수 있다.

**대응방안 (p.239)**
- 자동 연결할 **외부 URL·도메인을 화이트리스트로 관리**하고, 입력값이 화이트리스트에 존재하는지 확인.

**진단방법 (p.242~243)**
- ① 리다이렉션 함수(`response.sendRedirect`) 존재 확인 → ② 인자 url이 외부 입력값인지 확인. 외부 입력 변수가 아니면 안전. 외부 입력이면 **유효값 검사·화이트리스트 관리 시 안전**, 그대로 사용 시 취약.

**코드예제 (p.239~242)** — JAVA, C#
- 핵심 차이: 외부 입력 URL로 그대로 리다이렉트 → **이동 가능 URL 범위 제한(화이트리스트) 또는 로컬 URL 확인 후 이동**.

**오탐 주의사항 (p.243)**
- `HttpRequest.getContextPath()`는 **내장함수로 context path를 리턴**하므로 안전한 URL.

## 8. 부적절한 XML 외부개체 참조 (XXE) (CWE-611, p.244~250)

**정의 (p.244)**
- **서버가 XML 외부 엔티티를 처리하도록 설정된 경우** 발생. 취약한 XML parser가 외부 값을 참조하는 XML을 처리할 때 공격 구문이 동작하여 **서버 파일 접근, 자원 고갈, 인증 우회, 정보 노출** 가능.

**대응방안 (p.244)**
- **로컬 정적 DTD 사용** 설정. 외부 전송 XML의 **DTD 완전 비활성화**. 불가 시 **외부 엔티티·외부 문서 유형 선언을 파서별 고유 방식으로 비활성화**.

**진단방법 (p.247~250)**
- ① XML 파싱 여부 확인 → ② 신뢰할 수 없는 입력 파일에 대해 **외부 엔티티 비활성화 코드가 없으면 취약**. `SAXParserFactory` 사용 시 비활성화 누락이면 취약.

**코드예제 (p.244~247)** — JAVA
- 핵심 차이: 파서 제한 설정 없이 파싱 → **doctype 금지, 외부 일반/파라미터 엔티티 미포함, 외부 DTD 비활성화, XInclude 미사용, 엔티티 참조 노드 미확장** 설정 추가.

**오탐 주의사항 (p.248~250)**
- `DocumentBuilderFactory`/`SAXParserFactory` feature 제한 설정 시 안전. `SchemaFactory` 또는 `Validator`의 `setProperty()` 제한 설정 시 안전. `XMLInputFactory`의 `setProperty()` 제한 설정 시 안전.

## 9. XML 삽입 (XQuery/XPath Injection) (CWE-652, CWE-643, p.251~263)

**정의 (p.251)**
- 검증되지 않은 외부 입력이 **XQuery/XPath 쿼리문 생성 문자열**로 사용되어 쿼리 구조 변경·임의 쿼리 실행 → **허가되지 않은 데이터 열람, 인증절차 우회** 가능.

**대응방안 (p.251)**
- 외부 입력데이터의 **특수문자·쿼리 예약어 필터링**. **파라미터화된 쿼리문을 지원하는 XQuery** 사용.

**진단방법 (p.259~263)**
- [XQuery] ① 실행 부분 확인 → ② 쿼리스트링 변수의 외부 입력 여부 → 필터링 모듈 확인. [XPath] ① 쿼리 컴파일 부분 확인 → 동일. 필터링 모듈 또는 프레임워크 조치 시 안전.
- 취약 예: `name`에 `something' or '='1` → 파일 내 모든 값 출력; `passwd="' or "='"` → 인증 우회 로그인 (p.259, p.262).

**코드예제 (p.251~259)** — JAVA, C#
- 핵심 차이: 문자열 결합으로 표현식 생성 → **`login.xq` 등 파라미터화된 쿼리에 외부값 바인딩** 또는 `bindingString`/문자열 필터링으로 구조 변경 차단.

**오탐 주의사항**
- 별도의 `오탐코드의 예` 미제시 (문서 미기재). 필터링 모듈 존재·프레임워크 조치 시 안전 판정한다는 일반 원칙만 기재.

## 10. LDAP 삽입 (CWE-90, p.264~271)

**정의 (p.264)**
- 외부 입력으로 의도하지 않은 **LDAP 명령어**를 수행할 수 있는 보안약점. 프로세스는 **명령을 실행한 컴포넌트와 동일한 권한**으로 동작.

**대응방안 (p.264)**
- **DN과 필터**에 사용되는 입력값의 특수문자 제거. 특수문자(`= + < > # ; \` 등)를 써야 하면 **일반문자로 인식되도록** 처리.

**진단방법 (p.268~271)**
- ① LDAP 조회 쿼리 실행 확인 → ② **필터**에 쓰이는 변수의 외부 입력 여부 → ③ **필터링 모듈 존재** 확인. 필터링·프레임워크 조치 시 안전.
- 취약 예1: `name`에 `*` → `(name=*)` 항상 참 → 인증 우회. 취약 예2: 외부 입력이 검색 **base 문자열**에 사용 → 임의 루트 디렉터리 정보 접근.

**코드예제 (p.264~268)** — JAVA, C#, C
- 핵심 차이: `userSN`/`userPassword` 무검증 결합 → **LDAP 필터 조작 문자열 제거 + 익명 바인딩 대신 인증 후 쿼리 실행**.

**오탐 주의사항**
- 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 11. 크로스사이트 요청 위조 (CSRF) (CWE-352, p.272~275)

**정의 (p.272)**
- 사용자가 인지하지 못한 상황에서 **의도와 무관하게 공격자가 의도한 행위(수정·삭제·등록 등)를 요청**하게 하는 공격. 사용자가 **관리자**면 관리자 권한 기능이 공격자 의도대로 실행될 수 있다. 적법성 입증 값이 **고정**이고 **GET 방식**이면 쉽게 악용된다.

**대응방안 (p.272)**
- 입력 폼은 **GET 대신 POST**. 폼과 처리 프로그램 사이 **토큰** 사용. **중요 기능은 세션검증 + 재인증** 유도.

> 💡 현행 권고: 토큰 방식과 함께 세션 쿠키에 **SameSite 속성(Lax/Strict)** 설정을 병행하는 것이 현행 표준 방어다 (출처: OWASP CSRF Prevention Cheat Sheet).

**진단방법 (p.274~275)**
- ① 권한변경·신규등록 등 **주요 기능** 확인 → ② **권한확인 절차 존재** 확인. 절차가 없거나 **세션쿠키·사용자 IP·SSL 인증 등 자동 제출 자격증명**에만 의존하면 취약.

**코드예제 (p.272~274)** — JAVA, C#
- 핵심 차이: 검증 없는 요청 처리 → **임의 토큰 생성·세션 저장 → HIDDEN 필드 전달 → 요청 토큰과 세션 토큰 비교 일치 시에만 처리** (C#은 `AntiForgeryToken()`).

**오탐 주의사항 (p.274~275)**
- 세션 토큰과 HIDDEN 필드 토큰을 **비교하여 일치할 때만 처리**하는 코드는 오탐(취약하지 않음).

## 12. 서버사이드 요청 위조 (SSRF) (CWE-918, p.276~283)

**정의 (p.276)**
- 검증 없는 사용자 입력을 **서버 간 요청**에 사용하여 악의적 행위가 발생. 공격자는 URL·요청문 위조로 **접근통제 우회**, **신뢰된 네트워크의 데이터 획득** 가능.

**대응방안 (p.276)**
- 사용자 입력값의 서비스 호출은 **화이트리스트 필터링**. 무작위 URL을 받아야 하면 **내부 URL 블랙리스트 필터링**. 동일 내부망이라도 **기기 인증·접근권한 확인**.

**진단방법 (p.278~283)**
- ① 다른 시스템 서비스 호출 함수 확인 → ② 입력값의 신뢰 가능 여부 확인. 신뢰 불가 + 검증절차 없음 → 취약.
- `openConnection` URL을 **properties에서 참조**해도 위·변조 가능성으로 취약 판정. 공격 예: `/getFavicon?host=192.168.176.1:8080/secrets.txt?`.
- [참고] SSRF 우회 예시표 (p.281~283): 10진수/16진수/8진수 IP 표기, 오버플로 형식, IDNA2003 변환, Broken Parser(`#`, `@`), SSRF 이용 LFI.

**코드예제 (p.276~278)** — JAVA
- 핵심 차이: 사용자 입력 url 직접 연결 → **key/value URL 리스트(urlMap)를 두고 key만 입력받아 매핑된 URL로 접속**.

**오탐 주의사항 (p.280~281)**
- 클라우드 메타데이터 주소 `169.254.169.254` **블랙리스트 필터링 + HTTP(S) 스킴 체크** 시 취약하지 않음.
- `isPrivateIP()` 내부대역 블랙리스트: **"블랙리스트를 우회할 수 있는 다양한 공격을 감안해서 필터링하고 있는지 검토 후 취약 여부를 판단"** — 단순 오탐 처리 금지.

## 13. HTTP 응답분할 (CWE-113, p.284~289)

**정의 (p.284)**
- HTTP 요청 파라미터가 **응답헤더에 포함되어 재전달**될 때 CR·LF 개행문자가 있으면 **응답이 2개 이상으로 분리**될 수 있다. 두 번째 응답에 악성 코드를 주입하여 **XSS·캐시 훼손(Cache Poisoning)** 수행 가능.

**대응방안 (p.284)**
- 요청 파라미터를 응답헤더(`Set-Cookie` 등)에 포함시킬 경우 **CR·LF 개행문자 제거**.

**진단방법 (p.286~289)**
- ① Response 헤더에 변수 사용 확인 → ② 외부 입력값 여부 확인 → **개행문자(`\r`, `\n`) 필터링·검증 존재** 확인. 없으면 취약.
- `response.sendRedirect`는 이동 URL을 헤더에 입력하므로 공격자 입력이 쓰이면 응답 변경 가능.

**코드예제 (p.284~286)** — JAVA, C#
- 핵심 차이: 외부 입력을 그대로 헤더/쿠키에 설정 → **개행문자(`\r\n`) 제거 후 설정**.

**오탐 주의사항 (p.288~289)**
- 개행문자 필터링 후 쿠키 설정 시 안전. `getContextPath()`는 내장함수라 안전. **Long·Integer 등 Numeric 값**은 `\r\n` 포함 불가로 안전.

## 14. 정수형 오버플로우 (CWE-190, p.290~296)

**정의 (p.290)**
- 정수값이 허용된 최대값보다 커져 실제 저장 값이 **의도치 않게 아주 작은 수나 음수**가 되는 약점. 특히 **반복문 제어, 메모리 할당·복사** 조건에 사용자 입력값을 쓸 때 보안 문제 유발.

**대응방안 (p.290)**
- **언어·플랫폼별 정수타입 범위** 확인. 연산 **결과값 범위 체크 모듈** 사용. 외부입력값을 **동적 메모리 할당**에 쓸 때 적절 범위 확인.

**진단방법 (p.293~296)**
- ① 변수로 **배열 크기를 동적 결정**하는 경우 확인 → ② 외부 입력값 여부 확인 → 범위 검증 절차 없으면 취약. 외부 입력값이 **음수**면 배열 크기가 음수가 되어 취약.

**코드예제 (p.290~293)** — JAVA, C#, C
- 핵심 차이: 크기 검증 없이 정수형 사용 → **입력값 크기 검증 후 사용** (C#은 `checked` 구문).

**오탐 주의사항 (p.295~296)**
- `available()` 등 **int 리턴 함수** / **HTTP 헤더 한계값** 존재 / **인자 개수의 정수 한계 초과는 실현 희박** / **외부 값이 아닌 경우** — 모두 취약하지 않음.

## 15. 보안기능 결정에 사용되는 부적절한 입력값 (CWE-807, p.297~302)

**정의 (p.297)**
- **외부입력값 신뢰를 전제로 보호메커니즘을 사용**하면 입력값 조작으로 우회 가능. 개발자는 **쿠키·환경변수·히든필드**가 조작될 수 없다고 가정하지만 공격자는 변경할 수 있다. **충분한 암호화·무결성 체크** 없이는 외부 입력값을 신뢰하지 말 것.

**대응방안 (p.297)**
- **상태정보·민감 데이터(특히 세션정보)는 서버에 저장**, **보안확인 절차도 서버에서 실행**. 보안결정에 쓰이는 입력값을 식별하고 **입력값에 의존하지 않는 구조**로 변경 검토.

**진단방법 (p.300~302)**
- ① **인증여부 확인에 쓰는 변수** 확인 → ② **세션정보 등 서버 내부 검증값**인지 확인. **인증결정 기준으로 외부 입력값을 그대로 사용하면 취약**.
- 취약 예: 평문 인증정보·`"authenticated"`를 쿠키에 저장 — 쿠키 변경 가능. 중요 정보는 암호화하고 가급적 WAS **세션**에 저장.

**코드예제 (p.297~300)** — JAVA, C#, C
- 핵심 차이: HIDDEN 필드의 가격·인증정보를 그대로 사용 → **item만 받아 서버 보유 가격으로 계산**, 인증정보는 **쿠키 대신 세션**, 서버 주소는 **고정값** 사용.

**오탐 주의사항 (p.301~302)**
- HIDDEN 필드 `price`를 쓰지 않고 **서버에 정해진 가격을 사용**하면 취약하지 않음.

## 16. 메모리 버퍼 오버플로우 (CWE-119, p.303~308)

**정의 (p.303~304)**
- **할당된 메모리 범위를 넘어선 위치에 읽기/쓰기** 시 발생. 오동작 유발 또는 악성 코드 실행으로 프로그램 통제권 탈취. **스택/힙** 버퍼 오버플로우로 구분. `gets()` 같은 함수 사용 시 공격자가 **복귀 주소를 공격코드 시작주소로 덮어쓸 수 있다**.

**대응방안 (p.304)**
- **적절한 버퍼 크기 설정** 및 범위 내 읽기/쓰기 **통제**. 문자열은 **널(Null) 문자를 버퍼 범위 내에 삽입**하여 종료.

**진단방법 (p.305~308)**
- 버퍼 기록 시 **값 크기 < 버퍼 크기** 확인. 외부 입력값이 크기를 결정하면 충분성 확인. 크기 비교·인덱싱 시 **음수 방지(0보다 큰지) 반드시 확인**. **상수 접근**은 상수값 확인 및 버퍼 범위 고려 수정 필요. **반복문 버퍼 접근은 경계값 확인 필수**. 문자열 버퍼는 **마지막 널 문자 포함** 확인.
- 취약 사례: 16 byte 버퍼에 크기 검사 없이 복사; 외부 입력을 64 byte hostname으로 사용; 공백 제거 루프에서 인덱스 음수 미검사 (p.305~308).

**코드예제 (p.304~305)** — C
- 핵심 차이: `sizeof(cv_struct)`로 인접 포인터를 덮어씀 → **`sizeof(cv_struct.x)`로 변경 + 널 문자 삽입**.

**오탐 주의사항**
- 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 17. 포맷 스트링 삽입 (CWE-134, p.309~313)

**정의 (p.309)**
- 외부 입력값을 검증 없이 **입·출력 함수의 포맷 문자열로 사용**할 때 발생. 공격자는 **메모리 내용을 읽거나 쓸 수 있고** 프로세스 권한 취득·임의 코드 실행 가능. (부록 p.512 각주) 포맷 스트링: 입·출력의 형식·형태를 지정하는 문자열.

**대응방안 (p.309)**
- `printf()`, `snprintf()` 등에서 **사용자 입력값을 포맷 문자열로 직접 사용하거나 포맷 문자열 생성에 포함 금지**. 특히 **`%n`, `%hn` 사용 금지**(메모리 값 변경 가능). 사용자 입력은 **`%s` 지정 + 2번째 이후 파라미터**로.

**진단방법 (p.312~313)**
- 포맷 스트링 함수의 **인자에 포맷 스트링 포함 여부**와 **외부 입력값의 포맷 스트링 생성 사용 여부** 확인. 포맷 인자 개수와 매개변수 개수 일치 + 외부값 미사용이면 안전. **출력 데이터 길이 한정** 필요. 그 외 취약.
- 취약 예: `%1$tm, %1$te, %1$tY` 입력 시 문제 발생.

**코드예제 (p.309~312)** — JAVA, C
- 핵심 차이: 외부 입력값을 포맷 문자열로 사용 (`args[0]`에 `%1$tY-%1$tm-%1$te` 전달 시 시스템 날짜 노출) → **외부 입력값이 포맷 문자열 출력에 사용되지 않도록 수정**.

**오탐 주의사항**
- 별도의 `오탐코드의 예` 미제시 (문서 미기재).

# 제2절 보안기능 (16개, p.314~405)

## 18. 적절한 인증 없는 중요기능 허용 (CWE-306, p.314~318)

**정의 (p.314)**: 적절한 인증과정 없이 **중요정보(계좌이체 정보, 개인정보 등)를 열람·변경**할 때 발생.

**대응방안 (p.314)**
- **클라이언트 보안검사 우회로 서버 접근 불가**하게 설계. 중요 페이지는 **재인증**(은행 계좌이체 등). **검증된 라이브러리·프레임워크**(OpenSSL, ESAPI 보안기능 등) 사용.

**진단방법 (p.317~318)**
- **정적도구로 판단하기 어려워 진단원이 직접 코드에서 중요정보 여부를 파악**해야 한다.
- ① 비밀번호·개인정보(주민등록번호 등)·금융정보(카드·계좌)·게시글 수정/삭제 등 **중요정보·기능 정의** 여부 확인 → ② 접근·변경 시 **적절한 인증 확인 기능 구현** 여부 확인. 인증 확인이 있으면 안전.
- 취약 예: **재인증 없는 계좌이체**; **클라이언트 측 인증 수행**(우회 가능).

**코드예제 (p.314~317)** — JAVA, C#
- 핵심 차이: 로그인 사용자와 수정 대상 사용자의 **일치 확인 없이** 회원정보 수정 → **동일인 확인(자격인증) 후에만** 수정.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 19. 부적절한 인가 (CWE-285, p.319~324)

**정의 (p.319)**: **모든 실행경로에 대해 접근제어를 검사하지 않거나 불완전하게 검사**하면 공격자가 접근 가능한 실행경로 정보를 유출할 수 있다.

**대응방안 (p.319)**
- 정보·기능을 **역할에 따라 배분**하여 **공격노출면(Attack Surface) 최소화**. 사용자 권한별 **ACL** 관리. **JAAS Authorization Framework, OWASP ESAPI Access Control** 등 활용 가능.

**진단방법 (p.322~324)**
- **외부 시스템(웹서버·DB·LDAP) 권한 설정 관련이라 정적도구로 판단 곤란**. 중요정보 저장 **외부시스템 식별** + **접근·변경 권한 사전 정의** 확인.
- ① 해당 정보·기능 호출 함수에서 **정의된 권한 소유 검사** 여부 확인. 접근제어를 **JavaScript 등 클라이언트 측에서 제어해 우회 가능한지** 확인.
- 취약 예: 외부 입력 `name`이 동적 LDAP 쿼리 사용자명으로 쓰이고 접근제어 없음 — **anonymous binding 허용**으로 임의 사용자 정보 접근 가능.

**코드예제 (p.319~322)** — JAVA, C#, C
- 핵심 차이: delete 등 권한 확인 없이 수행 → **세션 사용자 정보로 작업 권한 확인 후 권한 있을 때만 수행**.

**오탐 주의사항 (p.323~324)**
- 세션 저장 사용자 정보로 **삭제작업 권한 확인 후 수행**하는 코드는 오탐(취약하지 않음).

## 20. 중요한 자원에 대한 잘못된 권한 설정 (CWE-732, p.325~329)

**정의 (p.325)**: **중요한 보안관련 자원에 읽기/수정 권한을 의도치 않게 허가**하면 비인가 사용자가 해당 자원을 사용하게 된다.

**대응방안 (p.325)**
- 설정파일·실행파일·라이브러리는 **SW 관리자만 읽고 쓰기 가능**하게 설정. 중요 자원 사용 시 **비인가 사용자 접근 가능 여부 검사**.

**진단방법 (p.328~329)**
- **정적도구로 중요자원 판단이 어려워 진단원이 직접 식별**해야 한다. SW가 생성하는 중요자원(파일 등) 식별 → **읽기·쓰기·실행 권한 사전 정의** 여부와 정의대로 허용하는지 확인. **설정파일·문서파일은 실행 권한 미설정** 확인.

**코드예제 (p.325~328)** — JAVA, C#, C
- 핵심 차이: 모든 사용자에게 읽기/쓰기/실행 허용 → **소유자에게 필요한 권한(읽기)만 허용**, `FileSystemAccessRule` 등으로 제한.

**오탐 주의사항 (p.329)**
- 실행·쓰기 권한을 제외하고 **읽기 권한만 부여**하면 취약하지 않다.

## 21. 취약한 암호화 알고리즘 사용 (CWE-327, p.330~336)

**정의 (p.330)**
- **base64 같은 단순 인코딩**으로는 비밀번호를 보호할 수 없다. 취약·위험 알고리즘과 **표준화되지 않은 자체 알고리즘**은 무력화 위험이 높다. **RC2, RC4, RC5, RC6, MD4, MD5, SHA1, DES**가 취약 알고리즘에 해당.

**대응방안 (p.330~331)**
- **자체 알고리즘 개발 금지**, 검증된 표준 알고리즘 사용. DES·RC5 등을 **3DES, AES, SEED** 등으로 대체. 업무내용·개인정보에는 **검증필 암호모듈**(IT보안인증사무국) 사용.
- [참고 표 p.331~332] 최소 안전성 112비트: 블록암호 ARIA(128/192/256)·SEED(128); 운영모드 ECB/CBC/CFB/OFB/CTR(기밀성), CCM/GCM(기밀성·인증); 해시 SHA-224/256/384/512; MAC HMAC·CMAC/GMAC; 난수 HASH_DRBG/HMAC_DRBG/CTR_DRBG; 공개키 RSAES(2048, 3072); 전자서명 RSA-PSS, KCDSA, ECDSA, EC-KCDSA; 키설정 DH, ECDH.

> 💡 현행 권고: 원문이 대체안으로 나열한 **3DES(TDEA)는 NIST SP 800-131A Rev.2에 따라 2023년 말 이후 사용 금지(disallowed)** 되었다. 대체는 AES·ARIA·SEED·LEA 등 128비트 이상 블록암호로 하라. 운영모드도 ECB는 실무상 회피할 것 (출처: NIST SP 800-131A Rev.2, NIST SP 800-38A). 알고리즘·키 길이 적합성의 정밀 판정은 `crypto-policy-kr` 스킬 참조.

**진단방법 (p.333~336)**
- 언어 제공 암호화 함수의 취약 알고리즘 사용은 도구·진단원이 확인 가능하나, **자체 암호화 알고리즘의 적절성 판단은 수동진단 필요**. **자체 구현 알고리즘 사용은 취약 판정** (암호전문가의 보증이 있으면 예외 판단 가능).
- 취약 알고리즘: **RC2, RC4, RC5, RC6, MD4, MD5, SHA1, DES 등**. 안전 알고리즘: **SHA-256, AES, SEED, ARIA 등**.

**코드예제 (p.330~333)** — JAVA, C#, C
- 핵심 차이: **DES** 사용 → **AES** 등 안전한 알고리즘 사용.

**오탐 주의사항 (p.333~334)** — 중요
- "**Base64 encoding은 암호화가 아닌 인코딩**이다. 가시성·보관성 목적의 Base64 사용은 취약한 암호화 알고리즘이라 하기 어렵다. **하지만 개발자가 암호화를 위해 Base64 encoding을 사용하였다면 취약하다고 판정한다.**"

## 22. 암호화되지 않은 중요정보 (CWE-312, CWE-319, p.337~349)

**정의 (p.337)**: 중요정보(개인정보·인증정보·금융정보 등)를 **평문으로 송·수신하거나 저장**하면 비인가 사용자에게 노출될 수 있다.

**대응방안 (p.337)**
- 중요정보 **저장·전송 시 반드시 암호화**. 읽기/쓰기 시 **권한인증**. 필요 시 **SSL/HTTPS 보안 채널**, 쿠키 저장 시 **보안속성 설정**(`setSecure(true)` 등).

**진단방법 (p.346~349)**
- **[평문저장]** 중요정보는 설계과정에서 결정되므로 **일반적으로 검사할 수 있는 기법은 존재하지 않는다**. 로그인·암호 사용 등 특정 경우 **메소드 인자 값 추적**으로 평문 유무 판단. 중요정보는 불필요한 참조 제거, 임시 변수도 암호화 확인, **사용 완료된 임시변수 값은 반드시 초기화**. 쿠키에는 저장하지 않거나 암호화 저장.
- **[평문전송]** 정적도구로 중요정보 기준 판단 곤란. **네트워크 전송 시 암호화·보안 채널 사용 여부** 확인. **URL 전송 시에도 암호화**. 쿠키 전송 시 암호화 + **`setSecure(true)`**. 절차 생략 시 취약.
- 취약 예: 소켓 수신 암호를 평문으로 파일 기록; DB 접속 ID/비밀번호 설정파일 평문 저장; 비밀번호 평문 네트워크 전송(스니핑 노출); 중요정보 URL 일반 채널 연결.

**코드예제 (p.337~346)** — JAVA, C#, C
- 핵심 차이: 비밀번호 평문 DB 저장/전송 → **솔트 포함 SHA-256 해시 저장**, 전송은 **AES-CBC 등 강력한 암호화(외부 키 사용) 후 전송**.

> 💡 현행 권고: 비밀번호 저장은 일반 해시(SHA-256+솔트)보다 **의도적으로 느린 전용 함수 — Argon2id, bcrypt, scrypt, PBKDF2 — 사용**이 현행 표준이다 (출처: OWASP Password Storage Cheat Sheet, NIST SP 800-63B). 판정 기준(암호화/해시 유무)은 원문 그대로 적용하되, 개선 권고 시 이를 제시하라.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 23. 하드코드된 중요정보 (CWE-259, CWE-321, p.350~359)

**정의 (p.350)**: 코드 내부에 **하드코드된 비밀번호·암호화키**로 내부 인증·암호화를 수행하면 중요정보가 유출될 수 있다. (부록 p.513) 소스코드 유출 시 노출되고 **주기적 변경이 어렵다**.

**대응방안 (p.350)**
- 비밀번호는 **암호화하여 별도 파일에 저장**. 암호화에는 **상수가 아닌 암호화 키** 사용, **소스코드 내 상수 형태 키 저장 금지**.

**진단방법 (p.357~359)**
- **[하드코드된 비밀번호]** 로그인(식별·인증) 모듈과 내·외부 서버(업무서버·DB) 접속 모듈에서 **비밀번호 직접 코딩** 여부 확인. 별도 파일 미저장 + 하드코딩이면 취약.
- **[하드코드된 암호화 키]** ① 비밀번호 사용 로직 확인 → ② 암호화 여부 확인 → ③ **암호화된 비밀번호가 소스 내 존재**하면 취약. **암호화 키의 소스 하드코딩**도 취약.

**코드예제 (p.350~357)** — JAVA, C#, C
- 핵심 차이: DB 비밀번호·암호화 키를 소스에 평문 상수로 저장 → **암호화된 비밀번호를 프로퍼티/외부 파일에서 읽어 복호화 사용**, 키도 외부 파일에 암호화 보관.

**오탐 주의사항 (p.359)**
- 상수가 **암호화 키가 아니라 알고리즘명을 지정**하는 경우는 취약하지 않다.

## 24. 충분하지 않은 키 길이 사용 (CWE-326, p.360~363)

**정의 (p.360)**: 검증된 알고리즘이라도 **키 길이가 충분하지 않으면 짧은 시간 안에 키를 찾아낼 수 있고**, 암호화된 데이터·비밀번호를 복호화할 수 있게 된다.

**대응방안 (p.360)**
- **RSA는 2,048비트 이상**, **대칭 알고리즘은 128비트 이상** 키 사용.

**진단방법 (p.363)**
- 기준: **대칭키(AES, ARIA, SEED 등) 128bit 이상 / 해시(SHA 등) 128bit 이상 / 공개키(RSA, DSA 등) 2,048bit 이상 (ECC는 256 이상)**. RSA라도 키를 작게 설정하면 취약.

> 💡 현행 권고: **2030년 이후까지 사용할 시스템은 RSA 3072비트 이상(128비트 보안강도)** 을 권장한다 (출처: NIST SP 800-57 Part 1 Rev.5; KISA 「암호 알고리즘 및 키 길이 이용 안내서」 — `crypto-policy-kr` 스킬 참조).

**코드예제 (p.360~363)** — JAVA, C#, C
- 핵심 차이: RSA 1024비트(또는 512비트) → **2048비트 이상**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 25. 적절하지 않은 난수 값 사용 (CWE-330, p.364~369)

**정의 (p.364)**: 예측 가능한 난수 사용 시 **공격자가 다음 숫자를 예상하여 시스템 공격** 가능.

**대응방안 (p.364)**
- 시드 고정 시 동일 난수 발생. Java `Random()`/`Math.random()`은 현재시간 기반 시드가 기본, **C `rand()`는 기본 시드가 없으므로 `srand()`로 매번 변경되는 시드 설정** 필요.
- **세션 ID·암호화키 등 보안결정용 값에는 `Random()`/`Math.random()` 금지** — 암호학적으로 보호된 **`java.security.SecureRandom`** 사용.

**진단방법 (p.367~369)**
- ① `Math.random()` 사용 확인 → **사용하면 취약**. ② **난수값을 세션ID 등 보안결정에 사용하는지** 확인 → 보안결정이면 `SecureRandom` 사용 시 안전.

**코드예제 (p.364~367)** — JAVA, C#, C
- 핵심 차이: 고정 시드로 동일 난수 → **`setSeed`로 가변 시드 또는 현재시간 기반**, 보안결정용은 **`SecureRandom`**.

**오탐 주의사항 (p.368~369)**
- **자체 랜덤 키 생성으로 보완**(Date 요소 등)한 경우 안전 판정. **`java.util.Random`·`java.security.SecureRandom` 사용 시 복잡도가 상대적으로 높아 취약하지 않다**.

## 26. 취약한 비밀번호 허용 (CWE-521, p.370~374)

**정의 (p.370)**: **강한 비밀번호 조합규칙을 요구하지 않으면** 사용자 계정이 취약해진다. **KISA 「암호이용안내서」의 비밀번호 설정규칙**을 적용해야 한다.

**대응방안 (p.370)**
- 비밀번호 생성 시 **강한 조건 검증**. **숫자·영문자·특수문자 혼합**, **주기적 변경**.

**진단방법 (p.373~374)**
- 생성·변경 시 규칙 검사 **모듈 존재** 확인. (참고) 안전한 조합규칙: **영문 대·소문자, 숫자, 특수문자 조합, 길이 8~10자리 이상**; **특정 패턴·사용자 ID 사용 금지**.
- **널 체크·자릿수·특수문자 요구 조건이 없거나 약하면 취약**. 복잡도 검증 없는 가입 승인도 취약.

**코드예제 (p.370~373)** — JAVA, C#, C
- 핵심 차이: 복잡도 체크 없이 등록(빈 비밀번호 허용) → **복잡도 체크 후 등록**.

**오탐 주의사항 (p.374)**
- **로그인 시 비밀번호 확인**은 저장이 아니므로 취약하지 않음. **저장 목적이 아닌 확인 목적**이면 취약하지 않다고 판정.

## 27. 부적절한 전자서명 확인 (CWE-347, p.375~378)

**정의 (p.375)**: 전자서명이 사용된 경우 **검증하지 않거나 절차가 부적절하면 위·변조된 파일로 악성코드에 감염**될 수 있다.

**대응방안 (p.375)**
- 전자서명 포함 파일 사용 시 **항상 전자서명 확인**. **출처 확인**으로 신뢰할 수 없는 파일 사용 금지.

**진단방법 (p.376~378)**
- `JarFile` 생성 시 **전자서명 확인 Boolean 파라미터가 있는 생성자 사용 여부** 확인. **`JarEntry.getCodeSigners()`로 서명 주체 검증 여부** 확인.
- 취약 예: 서명 확인 생성자는 썼으나 **서명 주체 검증 코드가 없으면 취약**.

**코드예제 (p.375~376)** — JAVA
- 핵심 차이: `new JarFile(f)` → **`new JarFile(f, true)` + `getCodeSigners()`로 주체 신뢰성 확인**.

**오탐 주의사항 (p.378)**
- **서명 확인 생성자 + 서명 주체 검증 코드**를 모두 사용하면 취약하지 않다.

## 28. 부적절한 인증서 유효성 검증 (CWE-295, p.379~381)

**정의 (p.379)**: 인증서를 확인하지 않거나 절차가 부적절하여 **악의적인 호스트에 연결되거나 신뢰할 수 없는 호스트의 데이터를 수신**하게 되는 약점.

**대응방안 (p.379)**
- 사용 전 유효성 확인: **Common Name과 실제 호스트 일치 / 신뢰된 발급기관(CA·RootCA) 서명 / 유효기간 / 해지 여부 / 안전한 암호화 알고리즘 사용 여부**.
- ⚠️ **원문 편집 오류**: 이 항목 `나. 보안대책` 첫 문단에 29번(영속 쿠키) 내용이 잘못 섞여 있다 (p.379). 인용 시 주의.

**진단방법 (p.381)**
- ① 인증서 확인 → ② **검증결과가 `X509_V_OK` 이외 값을 허용하는지** 확인. **신뢰되지 않은 발급기관·만료 인증서 허용은 위험**. ③ **Common Name** 확인. 미확인 사용 시 취약.

**코드예제 (p.379~381)** — C(안전하지 않은 예), JAVA(안전한 예)
- 핵심 차이: 자체 서명 인증서 가능 상태로 사용 → **호스트 인증서와 CA 인증서 DN 비교, CA 서명 여부, 유효기간 확인**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 29. 사용자 하드디스크에 저장되는 쿠키를 통한 정보 노출 (CWE-539, p.382~385)

**정의 (p.382)**: **개인정보·인증정보가 영속적인 쿠키(Persistent Cookie)에 저장**되면 공격자의 접근 기회가 많아져 시스템이 취약해진다.

**대응방안 (p.382)**
- 쿠키 **만료시간은 세션 지속 시간을 고려하여 최소로 설정**. **영속 쿠키에 권한 등급·세션ID 등 중요정보 포함 금지**.

> 💡 현행 권고: 만료시간 최소화와 함께 세션 쿠키에는 **`HttpOnly`·`Secure`·`SameSite` 속성**을 함께 설정하는 것이 현행 표준이다 (출처: OWASP Session Management Cheat Sheet).

**진단방법 (p.384~385)**
- ① 브라우저로 쿠키 전송 확인 → ② **쿠키 유효기간** 확인 → ③ 쿠키 값의 **중요 정보(id 등) 포함 여부** 확인.
- 취약 예: 만료시간을 **1년으로 과도하게 설정** — 하드디스크 저장으로 도용 위험.

**코드예제 (p.382~384)** — JAVA, C#
- 핵심 차이: 만료 1년 → **기능에 맞춰 최소로 설정**.

**오탐 주의사항 (p.385)**
- 만료시간을 **기능에 맞춰 최소로 설정**하면 안전.

## 30. 주석문 안에 포함된 시스템 주요정보 (CWE-615, p.386~389)

**정의 (p.386)**: 개발자가 편의상 주석에 비밀번호를 적어두면 **완성 후 제거가 어렵고**, 소스코드 접근 가능한 공격자가 쉽게 침입할 수 있다.

**대응방안 (p.386)**: 주석에 **ID·비밀번호 등 보안 관련 내용 기입 금지**.

**진단방법 (p.388~389)**
- ① **DB접속·관리자 로그인 구현 코드** 확인 → **주석의 암호 포함 여부** 확인. 취약 예: `DB연결 root / a1q2w3r3f2!@` 같은 주석.

**코드예제 (p.386~388)** — JAVA, C#, C
- 핵심 차이: 주석에 DB 연결 ID/비밀번호 기재 → **중요 정보를 주석에서 제거**.

**오탐 주의사항 (p.389)**
- 주석에 `"password"`, `"passwd"`, `"비밀번호"` 등 **텍스트만 있고 실제 내용이 비밀번호가 아니면** 취약하지 않다.

## 31. 솔트 없이 일방향 해쉬 함수 사용 (CWE-759, p.390~393)

**정의 (p.390)**: **솔트 없이 해시하여 저장**하면 **레인보우 테이블**로 비밀번호를 역산할 수 있다. (부록 p.513 각주) 솔트: 해시 적용 전 평문에 덧붙인 무의미한 데이터.

**대응방안 (p.390)**: **비밀번호와 솔트를 함께 해시하여 저장**.

> 💡 현행 권고: 22번과 동일 — 비밀번호 저장은 솔트가 내장된 **Argon2id·bcrypt·scrypt·PBKDF2** 사용이 현행 표준 (출처: OWASP Password Storage Cheat Sheet, NIST SP 800-63B).

**진단방법 (p.393)**
- ① `getInstance`로 **안전한 해시 알고리즘 인자의 `MessageDigest` 생성** 확인 → ② 반환 전 **`update` 함수에 솔트 사용** 확인. **솔트 없이 해시 값을 반환하면 취약**.

**코드예제 (p.390~393)** — JAVA, C#, C
- 핵심 차이: 솔트 미적용(NULL) → **솔트를 함께 해시**하여 원문 역산 차단.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 32. 무결성 검사 없는 코드 다운로드 (CWE-494, p.394~399)

**정의 (p.394)**: 원격에서 **소스코드·실행파일을 무결성 검사 없이 다운로드·실행**하면 **호스트 서버 변조, DNS 스푸핑, 전송 중 코드 변조**로 악성 코드가 실행될 수 있다.

**대응방안 (p.394)**
- **DNS 스푸핑을 방어할 수 있는 DNS lookup** 수행. 코드 전송 시 **신뢰할 수 있는 암호 기법으로 암호화**. 다운로드 코드는 **최소 권한으로 실행**.

**진단방법 (p.399)**
- ① **클래스 로드 코드** 확인 → 로드 전 **체크섬 실행·비교로 변조 여부 확인**하는지 확인. **체크섬 무결성 확인이 없으면 취약**.

**코드예제 (p.394~399)** — JAVA, C#, C
- 핵심 차이: 무결성 검사 없이 다운로드 → **공개키 방식 시그니처 생성·검증** 또는 **해시 값 무결성 검사**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 33. 반복된 인증시도 제한 기능 부재 (CWE-307, p.400~405)

**정의 (p.400)**: 일정 시간 내 반복 인증 시도에 **계정잠금·추가 인증 등 충분한 조치가 없으면**, 공격자가 사전(Dictionary) 기반 **무차별 대입(brute force)**으로 로그인·권한획득 가능.

**대응방안 (p.400)**
- **인증시도 횟수 제한**. 실패 횟수 초과 시 **계정 잠금 또는 추가 인증** 요구.

**진단방법 (p.404~405)**
- **인증 함수 호출 횟수 확인 + 호출 제한 코드 존재 여부** 확인. 없으면 취약. 취약 예: **반복문 안에서 제한 없이 인증 시도**.

**코드예제 (p.400~404)** — JAVA, C#, C
- 핵심 차이: 로그인 실패 무제한 → **연속 인증 시도 횟수 제한**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

# 제3절 시간 및 상태 (2개, p.406~418)

## 34. 경쟁조건: 검사 시점과 사용 시점(TOCTOU) (CWE-367, p.406~414)

**정의 (p.406)**
- 병렬시스템에서 자원(파일·소켓 등)의 **검사 시점(TOC)과 사용 시점(TOU)이 달라** 그 사이 상태가 변하는 약점. 예: A가 파일 존재를 검사한 뒤 읽으려는 순간 B가 삭제하여 오류 발생. **교착상태** 등도 유발.

**대응방안 (p.406)**
- 공유자원 접근에 **동기화 구문**(`synchronized`, `mutex` 등) 사용 — 한 번에 하나의 프로세스만 접근. **임계코드 주변만 동기화**하여 성능 영향 최소화.

**진단방법 (p.411~414)**
- ① **공유자원(파일/폴더·소켓·드라이버 등)의 다중 프로세스 사용** 확인. **동시 접근 가능성이 있으면 취약**, **동기화 구문 사용 시 안전**, **자체 pool 모듈 관리도 안전**.
- 참고: Java는 스트림 생성 시 `IOException` 처리로 대응 가능 — **TOCTOU는 주로 C 프로그래밍에서 발생** (p.412).

**코드예제 (p.406~411)** — JAVA, C#, C
- 핵심 차이: lock 없이 공유 자원 접근 → **`synchronized` / `mutex_lock`·`mutex_unlock`으로 동시 접근 제한**.

**오탐 주의사항 (p.413~414)**
- **실제로 경쟁 조건이 성립하지 않는 경우** 취약하지 않다.

## 35. 종료되지 않는 반복문 또는 재귀 함수 (CWE-674, CWE-835, p.415~418)

**정의 (p.415)**: **재귀 순환횟수를 제어하지 못하면** 메모리·스택 자원을 과다 사용. **귀납 조건(Base Case) 없는 재귀함수는 무한 루프 → 자원고갈 → 서비스 불능**.

**대응방안 (p.415)**: 모든 재귀 호출에 **횟수 제한** 또는 **초기값(상수) 설정으로 제한**.

**진단방법 (p.416~418)**
- **자신을 호출하는 재귀함수 식별** + **제어문으로 리턴 가능한지** 확인. 탈출 가능하면 안전. 재귀 판정 기준: **함수명 + 파라미터 개수 + 파라미터 자료형 일치**.

**코드예제 (p.415~416)** — C
- 핵심 차이: 탈출 조건 없는 재귀 → **탈출 조건 추가**.

**오탐 주의사항 (p.417~418)**
- **같은 이름·다른 파라미터 함수** 호출(오버로드)은 재귀가 아니므로 안전 (예: `func(String a)`에서 `func(int a)` 호출). **제어조건이 존재하는 재귀**는 취약하지 않다.

# 제4절 에러처리 (3개, p.419~432)

## 36. 오류 메시지 정보노출 (CWE-209, p.419~424)

**정의 (p.419)**: **민감한 정보를 포함하는 오류 메시지를 외부에 제공**하면 공격을 돕는다. **예외이름·스택 트레이스 출력**으로 내부구조가 노출된다.

**대응방안 (p.419)**
- 오류 메시지는 **최소한의 정보만 포함**. **예외상황은 내부적으로 처리**하고 사용자에게는 **미리 정의된 메시지** 제공.

**진단방법 (p.421~424)**
- **민감정보 기준은 정적도구가 판단하기 어려우므로 진단원이 출력값 중 민감 정보를 판단**해야 한다. ① 오류메시지 출력 시 **시스템 환경·유저정보·데이터 등 민감 정보 포함 여부** 확인. 내부 정보 유출 시 취약.

**코드예제 (p.419~421)** — JAVA, C#
- 핵심 차이: 스택·시스템 정보를 화면 출력 → **에러 코드·정보를 별도 정의하고 최소 정보만 로깅**.

**오탐 주의사항 (p.424)**
- `오탐코드의 예`가 제시되어 있으나 설명 문구가 정탐과 동일하게 기재됨 (**문서 설명 불명확**). 민감정보 노출 여부로 직접 판단하라.

## 37. 오류상황 대응 부재 (CWE-390, p.425~428)

**정의 (p.425)**: **오류 가능 지점을 확인하고도 예외 처리를 하지 않으면**, 공격자가 오류 상황을 악용해 의도하지 않은 동작을 유발할 수 있다.

**대응방안 (p.425)**: 오류 가능 부분에 **제어문으로 적절한 예외 처리** — C/C++ `if`/`switch`, Java `try-catch` 등.

**진단방법 (p.427~428)**
- **예외처리 수행 여부** + **예외 처리 루틴(제어문)이 비어있는지** 확인. 취약 예: `catch` 하고도 **아무 조치를 하지 않는 경우** — 어떤 일이 일어났는지 알 수 없게 됨.

**코드예제 (p.425~427)** — JAVA, C#
- 핵심 차이: `NullPointerException` 발생에 대응 없음 → **예외 사항에 적절한 조치 수행**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 38. 부적절한 예외 처리 (CWE-754, p.429~432)

**정의 (p.429)**: **함수 결과값의 적절한 처리 또는 예외상황 조건 검사를 하지 않으면** 예기치 않은 문제를 야기한다.

**대응방안 (p.429)**
- **값을 반환하는 모든 함수의 결과값 검사**. 예외 처리는 **광범위한 처리 대신 구체적인 예외 처리** 수행.

**진단방법 (p.431~432)**
- ① 반환값 검사·예외 발생 시 **구체적인 예외처리를 수행하는지** 확인.

**코드예제 (p.429~431)** — JAVA, C#
- 핵심 차이: 광범위한 예외처리 → **오류 종류·순서에 맞춘 세분화된 예외 처리**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

# 제5절 코드오류 (5개, p.433~468)

## 39. Null Pointer 역참조 (CWE-476, p.433~444)

**정의 (p.433)**: **"그 객체가 널이 될 수 없다"는 가정을 위반**했을 때 발생. 공격자가 의도적으로 발생시킨 **예외 상황을 추후 공격 계획에 사용**할 수 있다.

**대응방안 (p.433)**: 널 가능 **레퍼런스는 참조 전에 널 검사** 후 안전한 경우에만 사용.

**진단방법 (p.436~444)**
- 객체가 **널이 될 수 있는지** 확인. **널 체크 + 예외 처리 시 안전**, 미체크 시 취약.
- 널 가능성 판단 기준: 초기값 널 할당 / 선언 후 객체 미생성 / 널 객체의 필드 접근·메소드 호출 결과 / Nullable 객체 연산 결과.
- 대표 취약 패턴: 조건 분기로 값 미대입 상태 참조; DB `Connection`/`Statement`를 널 확인 없이 `finally`에서 참조; 널 가능 반환값(`enter2br()`) 참조; **널 검사를 했어도 조건문에서 널 객체 참조 구문을 먼저 비교**.

**코드예제 (p.433~436)** — JAVA, C#, C
- 핵심 차이: null인 `obj.equals()` 호출 → **참조 전 null 검사 후 사용**.

**오탐 주의사항 (p.441~444)** — 원문에서 가장 상세한 오탐 규칙
- **널을 리턴하지 않는 함수**(설계상 정의 포함) 리턴값 참조는 안전 — **Javadoc의 리턴 값 기술 확인** 필요.
- `try~catch`에서 **throw 시 catch 절 이후 미실행** → 역참조 없음.
- **앞 문장에서 이미 역참조가 발생**하면 뒤 문장은 실행되지 않음.
- **널 체크 조건이 참이면 OR 뒤 조건은 판단하지 않음**(단축 평가).
- `catch` 절에서 **return** 하면 예외 시 이후 코드 미실행.
- **JSP 내장 객체** 참조는 역참조 없음.
- **`Integer` 클래스 static 함수 호출**은 널 참조 아님.
- **단일 함수에서 파라미터가 널인 경우**는 취약하지 않은 것으로 판단(호출 측에서 널 체크).
- **JRE 기본 패키지 클래스 생성자**는 명시가 없는 한 널을 리턴한다고 판단하지 않음.

## 40. 부적절한 자원 해제 (CWE-404, p.445~453)

**정의 (p.445)**: 자원(파일디스크립터·힙 메모리·소켓 등)은 **유한**하다. **오류·에러로 사용 완료 자원을 반환하지 못하면** (부록 p.514) 자원이 고갈되어 새로운 입력을 처리할 수 없다.

**대응방안 (p.445)**: 사용 후 **반드시 자원 해제·반환**.

**진단방법 (p.450~453)**
- **자원 선언·할당 시 해제 여부** 확인. **제어문·예외처리문 분기에 따른 모든 control flow를 판단**하여 해제 여부 체크. **해제되지 않는 분기가 있으면 취약**.
- 취약 예: `rs.close()`, `pstmt.close()`를 `try~catch` 안에서 연속 수행 — 앞의 close에서 예외 발생 시 **이하 자원 미해제**.

**코드예제 (p.445~450)** — JAVA, C#, C
- 핵심 차이: 오류 시 미반환 → **`finally` 블록에서 각 자원별 null 검사 + 예외처리 후 해제** (C#은 `using` 구문).

**오탐 주의사항 (p.453)**
- **`finally` 절에서 close** 하면 안전. **함수의 역할이 자원을 리턴**하는 경우 해제는 **호출자 책임**이므로 취약하지 않다.

## 41. 해제된 자원 사용 (CWE-416, p.454~458)

**정의 (p.454)**: C 언어의 동적 메모리 관리 결함. **해제한 메모리를 참조**하면 예상치 못한 값·코드 실행으로 의도하지 않은 결과 발생.

**대응방안 (p.454)**
- 해제 후 포인터를 **참조 추적·형 변환·피연산자로 사용 금지**. **해제 후 포인터에 널(또는 적절한 값) 저장**으로 의도치 않은 실행 차단.

**진단방법 (p.456~458)**
- 메모리·파일 자원 사용 코드 확인. **자원 사용 코드 앞에서 해제가 발생하면 취약**. **해제 후 모든 제어 흐름이 사용 코드에 도달하지 않으면 안전**. 포인터 연산은 정밀 검사, **사용 완료 포인터의 초기화 여부** 확인.

**코드예제 (p.454~456)** — C
- 핵심 차이: 해제 자원 재참조·**이중 해제** → **최종 사용 후 해제 + 해제 후 NULL 할당**으로 이중 해제 무시.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 42. 초기화되지 않은 변수 사용 (CWE-457, p.459~461)

**정의 (p.459)**: C 언어의 **스택 지역변수는 자동 초기화되지 않는다**. 미초기화 변수 사용 시 임의 값으로 의도하지 않은 결과·동작 발생.

**대응방안 (p.459)**
- 미초기화 스택 변수는 **이전 함수에서 사용된 내용을 포함**한다 — 공격자가 **메모리 값 읽기·특정 코드 실행**에 악용 가능. **모든 변수를 사용 전 반드시 올바른 초기값으로 할당**.

**진단방법 (p.460~461)**
- **선언과 동시에 초기화** 여부 확인. **C++은 생성자에서 필드 초기화** 여부 확인. 미수행 시 기본적으로 취약. 취약 예: **디폴트 생성자에서 필드 미초기화** → 임의 값 보유.

**코드예제 (p.459~460)** — C
- 핵심 차이: 초기값 미지정 → **초기값 항상 지정**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 43. 신뢰할 수 없는 데이터의 역직렬화 (p.462~468)

**정의 (p.462)**
- **직렬화**: 인스턴스 상태를 바이트 스트림으로 복사. **역직렬화**: 바이트 스트림에서 객체 구조로 복원.
- **공격자가 전송·저장된 스트림을 조작할 수 있는 경우**, 신뢰할 수 없는 역직렬화로 **무결성 침해, 원격 코드 실행, 서비스 거부** 등이 발생할 수 있다.

**대응방안 (p.462)**
- **신뢰할 수 없는 데이터를 역직렬화하지 않도록** 구성. 암호화 통신 미적용 시 **송신 측 서명 추가 + 수신 측 서명 확인**으로 무결성 검증. 또는 **역직렬화 대상이 사전 검증된 클래스만 포함하는지 검증**하거나 **제한된 실행 권한으로 역직렬화 실행**.
- ⚠️ **원문 편집 오류**: `나. 보안대책` 앞 문단에 42번(초기화되지 않은 변수) 내용이 중복 기재 (p.462).

**진단방법 (p.466~468)**
- ① `java.io.ObjectInputStream.readObject()` 등 **역직렬화 함수** 확인 → ② **데이터의 신뢰 가능 여부** 확인. 출처를 신뢰할 수 없는 데이터의 **검증 절차가 없으면 취약**.
- 취약 예: `XMLDecoder`로 사용자 데이터 `readObject()` — 공격자 명령 실행 가능; 서버가 클라이언트 데이터를 검증 없이 역직렬화.

**코드예제 (p.462~466)** — JAVA
- 핵심 차이: 검증 없는 `readObject()` → **서명값 검증(불일치 시 예외) 후 읽기**, 또는 **`WhitelistedObjectInputStream`으로 `ObjectStreamClass` 클래스명 화이트리스트 확인, 없으면 예외**.

**오탐 주의사항 (p.467~468)**
- **HMAC으로 데이터 무결성을 검증**하는 경우 취약하지 않다고 판정 (클라이언트/서버 오탐 예 각각 제시).

**CWE 관련 주의**
- 원문 `마. 참고자료`(p.468)에 **CWE-918(SSRF)** 및 OWASP SSRF 링크가 기재 — 역직렬화와 무관한 **편집 오류**. 정확한 CWE 매핑은 **문서 미기재**이므로, 보고서에는 CWE 번호를 인용하지 말고 기준명("신뢰할 수 없는 데이터의 역직렬화")으로 인용하라.

# 제6절 캡슐화 (4개, p.469~491)

> 절 정의 (p.469): "중요한 데이터 또는 기능성을 불충분하게 캡슐화하거나 잘못 사용함으로써 발생하는 보안약점으로 정보노출, 권한문제 등이 발생할 수 있다."

## 44. 잘못된 세션에 의한 데이터 정보 노출 (CWE-488, CWE-543, p.469~475)

**정의 (p.469)**: **다중 스레드 환경에서 싱글톤 객체 필드에 경쟁조건**이 발생할 수 있다. Java 서블릿 등에서는 **정보 저장 멤버변수를 두지 말아** 서로 다른 세션 간 데이터 공유를 막아야 한다.

**대응방안 (p.469)**
- 싱글톤 패턴의 **변수 범위(Scope)에 주의**. **`HttpServlet` 하위클래스에 멤버 필드를 선언하지 않고**, 필요하면 **지역 변수** 사용.

**진단방법 (p.473~475)**
- **`HttpServlet` 하위클래스에 `final`이 아닌 멤버필드가 선언되면 취약**. 서블릿(JSP 포함)에서 **상수가 아닌 멤버 변수** 사용 시 취약.

**코드예제 (p.469~473)** — JAVA, C#
- 핵심 차이: JSP/Controller에서 String·int **멤버 변수** 선언(스레드 간 공유) → **지역변수(또는 세션변수)로 선언**.

**오탐 주의사항 (p.474~475)**
- JSP·서블릿 내 **내부 클래스**는 멤버필드가 아니므로 안전. **`final` 필드**(상수)는 안전. **Spring 기반 eGov 프레임워크는 IoC로 인스턴스를 관리**하므로 안전.

## 45. 제거되지 않고 남은 디버그 코드 (CWE-489, p.476~480)

**정의 (p.476)**: 디버그 코드는 **설정 등 민감 정보·시스템 제어 허용 부분**을 담을 수 있다. 배포에 남으면 **식별 과정 우회, 정보·제어 정보 노출** 가능.

**대응방안 (p.476)**
- 배포 전 **디버그 코드 확인·삭제**. Java 웹 개발에서 **`main()`에 만든 디버그 코드는 디버깅 종료 후 `main()` 메서드를 삭제**.

**진단방법 (p.479~480)**
- **J2EE를 제외하면 정적도구만으로 판단이 쉽지 않다**. ① 테스트 목적의 **잔존 디버그 코드** 확인. **J2EE 표준은 `main` 메소드 작성을 금지**하므로 **`main` 메소드가 있으면 디버그 코드인지 확인**하고 삭제.

**코드예제 (p.476~479)** — JAVA, C#
- 핵심 차이: `Console.WriteLine`/`main()` 등 디버그 코드 잔존 → **삭제**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 46. Public 메소드부터 반환된 Private 배열 (CWE-495, p.481~486)

**정의 (p.481)**: **private 배열을 public 메소드로 반환**하면 **배열 레퍼런스가 외부에 공개**되어 외부에서 **배열 수정·객체 속성 변경**이 가능해진다.

**대응방안 (p.481)**
- private 배열을 public 메소드로 반환하지 않는다. **복사본을 반환**하고 원소는 **`clone()`으로 복사**하여 저장. 원소가 **String 등 불변**이면 배열 복사본만 반환.

**진단방법 (p.484~486)**
- ① **private 배열 선언** 확인 → ② **public 메소드에서 반환되면 취약**. 원소가 일반 객체면 **원소별 객체 생성·값 복사 여부** 확인.
- 중요 취약 패턴: 새 배열을 만들어 `for`문 복사했어도 **원소가 일반 객체면 주소값만 복사되어 취약**.

**코드예제 (p.481~484)** — JAVA(원소가 일반객체 / String 등 불변), C#
- 핵심 차이: private 배열 그대로 return → **메소드를 private으로 하거나 복제본 반환 + 원소까지 `clone()` 복사** (수정용 public 메소드는 별도 제공).

**오탐 주의사항 (p.486)**
- **private가 아니고 `final`인 배열**은 취약하지 않다.

## 47. Private 배열에 Public 데이터 할당 (CWE-496, p.487~491)

**정의 (p.487)**: **public 메소드의 인자를 private 배열에 저장**하면 private 배열을 **외부에서 접근하여 수정·속성 변경**이 가능해진다.

**대응방안 (p.487)**
- public 메서드 인자를 private 배열에 직접 저장하지 않는다. **인자 배열의 복사본 생성 + `clone()` 원소 복사** 후 private 변수에 할당. 원소가 **String 등 불변**이면 복사본 생성·할당.

**진단방법 (p.490~491)**
- ① **private 배열 선언** 확인 → ② **public 메소드 인자 배열을 private 필드에 직접 할당하면 취약**. 원소가 일반 객체면 원소별 복사 여부 확인.
- 핵심 문장: "`userRoles` 필드는 private이지만, public인 `setUserRoles()`로 외부 배열이 할당되면 **사실상 public 필드가 된다**."
- 새 배열 `for`문 복사여도 **원소가 일반객체면 주소값만 복사되어 취약**.

**코드예제 (p.487~490)** — JAVA(원소가 일반객체 / String 등 불변), C#
- 핵심 차이: 인자 배열 직접 할당 → **복사본 생성 + 원소 `clone()` 복사 할당**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

# 제7절 API 오용 (2개, p.492~503)

## 48. DNS lookup에 의존한 보안결정 (CWE-247, p.492~496)

**정의 (p.492)**
- **공격자가 DNS 엔트리를 속일 수 있으므로 도메인명에 의존한 보안결정(인증·접근통제 등)을 하지 않아야 한다.** DNS 캐시 오염 시 **트래픽이 공격자를 경유**하거나 공격자가 **동일 도메인 서버로 위장** 가능.

**대응방안 (p.492)**: **보안결정에서 도메인명 기반 DNS lookup 금지**.

**진단방법 (p.495~496)**
- ① **DNS lookup 모듈 존재** 확인 → ② **보안결정 부분 존재** 확인. DNS 이름으로 신뢰를 검사하면 **캐시 조작 시 잘못된 신뢰 상태** 획득 가능.

**코드예제 (p.492~495)** — JAVA, C#, C
- 핵심 차이: **호스트 이름(도메인)으로 신뢰 판별** → **실제 서버의 IP 주소를 직접 비교**하여 DNS 변조 방어.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).

## 49. 취약한 API 사용 (CWE-676, CWE-242, CWE-246, CWE-382, p.497~503)

**정의 (p.497)**
- 취약한 API = **보안상 금지된(banned) 함수** 또는 **부주의하게 사용될 가능성이 많은 API**. 금지 API 대표 예: **`strcat()`, `strcpy()`, `strncat()`, `strncpy()`, `sprintf()`** 등. **잘못된 방식의 함수 사용**도 보안 문제 유발.

**대응방안 (p.497)**
- 금지 함수는 **안전한 대체 함수** 사용: `strcat_s()`, `strcpy_s()`, `strncat_s()`, `strncpy_s()`, `sprintf_s()`.
- 금지는 아니나 취약한 API 예: **`strtol()`** — 작은 크기의 부호 있는 정수 변환에 쓰면 범위 제한 없이 값 평가 가능.
- **개발 조직이 취약 API 분류를 명시했다면 반드시 준수**.

**진단방법 (p.501~503)**
- **취약 API 리스트를 작성**하고 사용 여부 확인. 사용 시 취약 판정. **대체 API가 없으면 인자·반환값 검사 여부** 확인.
- 취약 판정 사례: `strcpy()` 사용; **J2EE에서 `System.exit()` 사용**(웹 컨테이너 종료 가능).

**코드예제 (p.497~501)** — C, JAVA, C#
- 핵심 차이: `gets()` 등 길이 제한 불가 함수, 프레임워크 메소드 대신 소켓 직접 사용, J2EE `System.exit()` → **`gets_s()` 등 길이 제한 함수, 보안기능 제공 프레임워크 메소드, `System.exit()`/`Application.Exit()` 미사용**.

**오탐 주의사항**: 별도의 `오탐코드의 예` 미제시 (문서 미기재).
