# 모바일 전자정부서비스 앱 소스코드 검증 레퍼런스 스킬

> 근거 문서: 「모바일 전자정부서비스 앱 소스코드 검증 가이드라인」 행정안전부·한국인터넷진흥원(KISA), 2021.10, 총 51페이지.
> 이 스킬의 모든 페이지 표기 `(p.N)`은 위 원문 기준이다. **원문에 없는 내용은 "원문 미기재"로 명시한다.**

## 1. 개요

- 행정기관·공공기관 등이 개발한 **모바일 전자정부서비스 앱**을 전문기관(**한국인터넷진흥원, KISA**)에 소스코드 검증 신청할 때의 **검증 절차와 검증기준**을 규정한다 (p.10).
- 목적: 소스코드 수준의 SW 보안약점을 **사전 진단·제거**하여 안전성·신뢰성이 확보된 앱을 보급 (p.10).
- 적용 대상: **신규(기능개선 포함)로 개발되는 모바일 앱·하이브리드 앱(앱+웹)** 에 한정. 모바일 웹·반응형 웹은 대상이 아니며, 단순 컨텐츠(텍스트·이미지) 변경도 대상이 아니다. 신청기관 요청 또는 전문기관 필요 시 **앱(웹) 서버도 확장 점검** 가능 (p.11). 행정용 앱도 신청 시 검증 가능 (p.17).
- 직접 근거 지침: 「모바일 전자정부 서비스 관리 지침」(행정안전부예규) — 소스코드 보안약점 26개(별표 3)와 '모바일 앱 보안취약점' 점검기준 20개(별표 1)의 근거 (p.22, p.25). 관련 법령: 전자정부법, 개인정보 보호법 제24조③·제15조·제21조, 위치정보법 제18조·제23조 등 (p.10, p.26~27).

## 2. 검증 절차 흐름

3단계 개관 (p.17):

```
[준비 및 신청]            [앱 소스코드 검증]            [배포 및 서비스]
 제출물 준비        →      소스코드·기능보안성 점검   →   각 기관이 민간 앱스토어에
 (보안명세서, 실행 앱,      보안조치 및 조치내역 확인      개별 등록하여 배포
  소스코드) + 검증 신청     (최초 진단 후 보안조치 확인)
 ※ 검증 수요에 따라 검증대기 발생 가능
```

세부 절차 (p.18~20):

```
❶ 제출물 준비·검증 신청 ─→ ❷ 접수(접수증 발급, 검증반 할당) ─→ ❸ 앱 소스코드 검증
                                                                   │
                                        취약점 발견 ◄──────────────┤ 취약점 미발견
                                            │                      │
                     ❹ 보완요청서 발송 → 앱 소스코드 보완           │
                        (신청기관: 4주 이내 재제출)                 │
                            │                                      ▼
                     ❺ 보완조치 확인 ────────────────→ ❻ 결과보고서 통보·검증 종료
                                                                   │
                                                                   ▼
                                                      ❼ 배포 및 서비스 (앱스토어 등록)
```

| # | 단계 | 주체 | 산출물 / 내용 |
|---|---|---|---|
| ❶ | 제출물 준비·검증 신청 | 신청기관 | 신청서(붙임 제1호)·보안명세서(붙임 제2호), 공문은 온라인·제출물은 오프라인(방문/등기우편) (p.18~19) |
| ❷ | 접수 | 전문기관(KISA) | 접수번호 표기 **접수증(붙임 제3호)** 발급, 검증반 할당 (p.18~19) |
| ❸ | 앱 소스코드 검증 | 전문기관 | 소스코드 보안약점 + 기능 보안취약점 요구수준 충족 여부 검증. 착수 후 **2주** 소요 (p.18~19) |
| ❹ | 보완요청 → 보완 | 전문기관 → 신청기관 | **보완요청서(붙임 제4호)** → **보완조치내역서(붙임 제5호)** + 보완된 제출물, **4주 이내** 재제출 원칙 (p.18~19) |
| ❺ | 보완조치 확인 | 전문기관 | 조치내역 확인, 소요기간은 ❸과 동일 (p.19) |
| ❻ | 결과보고서·검증 종료 | 전문기관 | **결과보고서(붙임 제6호)** 를 공문으로 통보 (p.18~19) |
| ❼ | 배포 및 서비스 | 신청기관 | 최종 수정사항 확인 후 민간 앱스토어 등록·배포, 범정부EA포털(https://geap.go.kr) 등록 (p.20) |

**중도 종료 기준** (p.19): 보완요청 이후 **4주 경과** 또는 **동일 사항 보완요청 2회 초과** 시 전문기관이 검증종료 통보 가능. 검증 순서는 접수번호 순.

## 3. 검증기준 한눈에 보기

검증기준 = **(제1절) 소스코드 보안약점 26개** + **(제2절) 기능 보안취약점 FV-1~FV-9(세부 25개)** = 총 51개 항목 (p.22, p.25, p.35).

### 3.1 소스코드 보안약점 — 7개 유형 26개 항목 (p.22~24)

| 유형 | 항목 수 | 대표 항목 |
|---|---|---|
| 1. 입력데이터 검증 및 표현 | 5 | SQL 삽입, 경로 조작 및 자원 삽입, XSS, OS 명령어 삽입, 오버플로우 |
| 2. 보안기능 | 8 | 취약한 암호화 알고리즘, 중요정보 평문 저장/전송, 하드코드된 비밀번호/암호화 키 |
| 3. 시간 및 상태 | 1 | 경쟁조건(TOCTOU) |
| 4. 에러처리 | 3 | 오류 메시지 정보노출, 오류 상황 대응 부재, 부적절한 예외 처리 |
| 5. 코드오류 | 2 | Null Pointer 역참조, 부적절한 자원 해제 |
| 6. API 오용 | 1 | 취약한 API 사용 |
| 7. 모바일 환경 특화 | 6 | 컴포넌트 부적절한 접근 허용, 암시적 intent, 저장소 접근제어, 권한 검사 우회, 클래스 로딩 하이재킹, 난독화 미적용 |

> "모바일 환경 특화" 항목은 **CWE, CWE/SANS Top 25, OWASP Mobile Top 10** 등 공개영역 기준으로 제거해야 한다 (p.24).

### 3.2 기능 보안취약점 — FV-1 ~ FV-9, 세부 25개 (p.25~28, p.35)

| 코드 | 대분류 | 세부 항목 수 | 핵심 내용 |
|---|---|---|---|
| FV-1 | 임의기능 | 2 | 명세되지 않은 기능·악성행위 기능 존재 여부 |
| FV-2 | 최소권한 | 5 | 관리자 권한 동작, 미인가 API, UID 공유, 과도한 권한, 인텐트 권한 |
| FV-3 | 입력값 유효성 | 1 | 외부 입력값 유효성 검증 기능 존재 여부 |
| FV-4 | 중요정보 관리 | 8 | 개인정보/위치정보/비밀번호 암호화, 동의, 인증 방법, 비밀번호 조합규칙, 서버 점검 |
| FV-5 | 플랫폼 보안모델 | 2 | 루팅·탈옥 등 플랫폼 변조, 플랫폼 보안기능 사용 적절성 |
| FV-6 | 상용/공개용 모듈 | 2 | 모듈 사용 목적·기능, 개발사 안전성 확인 |
| FV-7 | 공개영역 취약점 | 1 | 플랫폼 알려진(및 신규) 취약점 |
| FV-8 | 모바일 대국민 보안공통기반 | 2 | 공통기반 기능 구현 적절성, 미적용 시 상응 보안 제공 |
| FV-9 | 기타 | 2 | 서비스 특화 취약점, 코드 난독화 도구 사용 여부 |

세부 51개 항목 전체 목록과 관리지침 별표1(20개 항목) 대응표는 `references/verification-criteria.md` 참조.

## 4. 모바일 특화 점검 포인트

> 원문에 실제로 기재된 항목만 다룬다. Intent 관련 항목은 원문이 모두 **Android 기준**으로만 기술한다 (iOS URL Scheme은 원문 미기재).

### 4.1 앱 위·변조 탐지 (FV-8) (p.28~29)

- 보안공통기반 미적용 앱은 공통기반 제공 기능(앱 위·변조 등)에 **부합되는 보안을 자체 제공**해야 한다 (FV-8.2).
- 적용 방법: 상용 위·변조 탐지 솔루션 도입 **또는** 기관 자체 구현 (p.28).
- 원문 구현 예시 — 앱 설치 시 위·변조 탐지 흐름 (p.29):

```
① (기관) 앱 서버 : 배포 전 실행파일(.apk) 해시값 생성·보관
② (사용자) 앱   : 설치 시 .apk 해시값 생성 → 앱 서버로 전송
③ (기관) 앱 서버 : 단말 해시값 ↔ 보관 해시값 비교 → 위·변조 여부 회신
                   ※ 앱-서버 간 E2E 암호화(TLS 통신 등) 적용 권고
④ (사용자) 앱   : 위·변조 확인 시 팝업으로 설치 중지·삭제 유도
```

**진단 시 확인할 것**: 해시 생성에 `java.security.MessageDigest` 사용 여부 (p.29 각주), 해시 비교가 **서버 측**에서 수행되는지, 앱–서버 통신에 TLS 적용 여부, 보안명세서의 "앱 위·변조 — 적용/적용 안함" 기재와 실제 구현 일치 여부 (p.41).

### 4.2 루팅/탈옥 등 플랫폼 변조 (FV-5) (p.27, p.35)

- FV-5.1: 루팅·탈옥 등 **플랫폼 변조 기능 존재 여부**. FV-5.2: 플랫폼 제공 보안기능 사용의 적절성.
- 기준 취지: 구현기능은 **모바일 플랫폼의 보안모델에 위배되지 않아야** 한다 (p.27).
- **진단 시 확인할 것**: 앱 내에 플랫폼 변조(루팅·탈옥)를 유발하는 기능이 없는지, 플랫폼 보안기능을 우회하지 않는지. 관리지침 별표1 대응 항목은 "9. 루팅 및 탈옥 기기에서의 정상 동작" (p.36). ※ 구체적 루팅 탐지 API·구현 방법은 원문 미기재.

### 4.3 중요정보 저장·전송 (FV-4 + 보안기능/모바일 특화 약점) (p.23~26, p.35)

| 대상 | 요구사항 | 근거 |
|---|---|---|
| 주민등록번호·여권번호·면허번호·외국인등록번호·금융정보 | 암호화 저장·전송 | FV-4.1, 개인정보 보호법 제24조③ |
| 비밀번호·바이오정보 | **일방향 암호화** 저장 | FV-4.2 |
| 개인위치정보 | 암호화 저장·전송 | FV-4.3, 위치정보 보호조치 권고 제8조 |
| 기타 중요정보 | 암호화 저장·전송 | FV-4.4 |

**진단 시 확인할 것**:
- 내·외부 저장소(SD카드 등)에 중요정보를 **암호화 없이 저장**하지 않는지 — 소스코드 보안약점 "접근제어 없이 내·외부 저장소 사용" (p.24, p.34).
- 소스코드 측 대응 약점: 중요정보 평문 저장/전송, 취약한 암호화 알고리즘, 충분하지 않은 키 길이, 하드코드된 비밀번호/암호화 키 (p.23).
- 보안명세서와 대조: 수집/저장/전송 구분별 개인정보 항목, 보안조치(동의, SHA-256 해시 저장, AES 암호화 전송 등), 저장/전송 경로(소스 파일 경로) 기재 (p.41).
  - 📋 위의 "SHA-256 해시 저장"은 **원문(2021) p.41의 보안명세서 기재 예시**를 그대로 옮긴 것이다 — 비밀번호 저장의 적정 조치를 보증하는 표현이 아니다.
  - ✅ 현행 권고: 비밀번호 저장은 **솔트+스트레칭 방식의 전용 KDF**(Argon2id/bcrypt/PBKDF2 등)를 사용하라 → `crypto-policy-kr` 3항 참조 (출처: OWASP Password Storage Cheat Sheet). 📕 단, **검증 신청 시 제도 판정은 원문 기준**(FV-4.2 일방향 암호화 충족 여부)을 따른다.
- **iOS**: 암호키 저장 시 **키체인(Keychain)** 사용 (p.41). 공통기반 사용 시 전송데이터 암호화에 **공통기반 VPN** 사용 (p.41).

### 4.4 인증 / 비밀번호 정책 (FV-4.6~4.7) (p.26, p.35)

- 민원인은 **아이디+비밀번호**, 신분증명 필요 시 **공동인증서** 사용 (p.26).
- 비밀번호 조합규칙: 영문·숫자·특수문자 등 조합 — 본문(p.26)은 "8자리 이상", 별표 제2호 FV-4.7(p.35)은 "9자리 이상"으로 **원문 내 수치가 상이**하다[^pw]. KISA 「패스워드 선택 및 이용 안내서」 참고.
- **진단 시 확인할 것**: 비밀번호 검증 로직(정규식/조합규칙), 인증 방법의 적절성(FV-4.6).

### 4.5 앱 간 통신 — Intent / 컴포넌트 접근제어 (Android) (p.24~25, p.34~35)

**진단 시 확인할 것**:
- `AndroidManifest.xml`의 컴포넌트(Activity/Service/Receiver/Provider) 접근 설정 — "컴포넌트의 부적절한 접근 허용"으로 외부 앱이 의도치 않게 실행 가능한지 (p.24, p.34).
- 민감정보 전송에 **암시적(implicit) intent** 를 쓰지 않는지 — 도청·악성행위 삽입 가능 (p.24, p.34).
- **권한 검사 우회** — 권한 없는 호출 프로그램이 앱 권한을 사용하게 되는 구조가 없는지 (p.24, p.34).
- **클래스 로딩 하이재킹** — 클래스 로드 디렉토리 경로를 공격자가 제어할 수 없는지 (p.24, p.34).
- **인텐트 권한의 올바른 설정 여부** (FV-2.5, Android) (p.25, p.35).
- 보안명세서와 대조: Android 앱은 해당 기능의 **Activity명·intent-filter** 기재 (p.42).

### 4.6 권한(퍼미션) / 최소권한 (FV-2) (p.25, p.35~36)

**진단 시 확인할 것**:
- 관리자 권한 동작(권한상승 포함) 기능 존재 여부 (FV-2.1, 공통).
- 인가되지 않은 API 사용 (FV-2.2, 공통).
- 동일 개인키로 서명된 다른 앱과 **UID 공유** 여부 (FV-2.3, Android) — 앱 서명 관점 점검.
- `AndroidManifest.xml` 에 선언된 **요청 권한과 실제 기능 사용의 부합** 여부 (FV-2.4, Android) ↔ 관리지침 "3. 불필요하거나 과도한 권한 설정" (p.36).
- 참고: 「스마트폰 앱 접근권한 개인정보보호안내서」 (p.12).

### 4.7 난독화 / 역공학 방지 (FV-9.2 + 소스코드 약점) (p.24, p.28, p.30, p.34~35)

- 안드로이드 앱은 디컴파일 도구(예: **apktool**)로 .apk를 소스 수준으로 쉽게 변환 가능 → **난독화 도구 적용 패키징 필수** (p.30).
- 상용 난독화 도구 권고, 불가 시 최소한 구글 오픈소스 **ProGuard** 적용(단, 오픈소스는 상용 수준의 기능·보안성을 담보하지 않음) (p.30).
- ProGuard 적용 — main module `build.gradle`, `minifyEnabled true` (p.30 원문 예시):

```gradle
buildTypes {
    debug {
        minifyEnabled true
    }
    release {
        minifyEnabled true
        proguardFiles getDefaultProguardFile('proguard-android.txt'), 'proguard-rules.pro'
    }
}
```

**진단 시 확인할 것**: `build.gradle`의 `minifyEnabled` 값, `proguardFiles` 설정, 보안명세서 "소스코드 난독화 — 적용/적용 안함" 기재 일치 (p.41). 소스코드 보안약점 "소스코드 난독화 미적용"(p.24)과 FV-9.2(p.35) 양쪽에서 점검.

### 4.8 기타 (p.25, p.27~28, p.33, p.35)

- **FV-1.2 악성행위 기능**: 불법 녹음, 임의 데이터 전송, 임의 위치정보 수집·전송 등이 없는지. 보안명세서 기능설명과 실제 기능의 일치(FV-1.1) (p.25).
- **FV-6 상용/공개 모듈**: 소스코드 미제공 모듈의 사용 목적·기능 적절성, 개발사의 안전성 확인 방법·결과. 보안명세서에 라이브러리 출처·URL·기능·위치·버전 기재 (p.27, p.40).
- **FV-7.1 공개 취약점**: Android/iOS/윈도우모바일 등 플랫폼의 알려진(및 신규) 취약점 (p.28).
- **오류/디버깅 정보 노출**: 오류 메시지·스택 정보에 시스템 내부 데이터/디버깅 정보가 공개되지 않는지 (p.33).
- **FV-4.8 앱(웹) 서버 점검**: 필요 시 수행. 관리지침 "18. 파일 다운로드 시 외부주소 변조 및 파일 무결성 우회" 대응 (p.35~36).

## 5. 점검 체크리스트

진단자는 아래 순서로 점검한다.

**[사전 준비]**
- [ ] 제출물 확인: 신청서, 보안명세서, 컴파일 가능한 소스코드 일체 + 실행파일(.apk/.ipa 등) (p.18)
- [ ] 보안명세서 정독: 식별정보·보안속성(권한, 중요정보, 난독화/위변조 적용 여부)·구현기능(Activity명, intent-filter, 상용모듈) (p.39~42)

**[소스코드 보안약점 — 26개 항목]** (p.22~24)
- [ ] 입력데이터 검증(5): SQL 삽입, 경로 조작, XSS, OS 명령어 삽입, 오버플로우
- [ ] 보안기능(8): 암호 알고리즘·키 길이, 평문 저장/전송, 하드코드된 비밀번호/키, 난수, 주석 내 주요정보
- [ ] 시간·상태(1) / 에러처리(3) / 코드오류(2) / API 오용(1)
- [ ] 모바일 특화(6): Manifest 컴포넌트 접근, 암시적 intent, 저장소 접근제어, 권한 검사 우회, 클래스 로딩, 난독화

**[기능 보안취약점 — FV-1 ~ FV-9]** (p.25~28, p.35)
- [ ] FV-1: 보안명세서 기능설명 ↔ 실제 앱 기능 일치, 악성행위 기능(녹음·임의전송·위치수집) 부재
- [ ] FV-2: 권한상승 기능, 미인가 API, UID 공유(서명 키), Manifest 권한 ↔ 기능 부합, 인텐트 권한
- [ ] FV-3: 외부 입력값 유효성 검증(길이 초과, 악성코드 포함 등)
- [ ] FV-4: 개인정보/비밀번호(일방향)/위치정보/기타 중요정보 암호화, 수집·활용 동의, 인증 방법, 비밀번호 조합규칙[^pw]
- [ ] FV-5: 플랫폼 변조(루팅·탈옥) 기능 부재, 플랫폼 보안기능(iOS 키체인 등) 사용 적절성
- [ ] FV-6: 상용/공개 모듈 목적·기능·안전성 확인 내역
- [ ] FV-7: 플랫폼 공개 취약점(CVE 등 알려진·신규 취약점)
- [ ] FV-8: 보안공통기반 기능 구현 적절성 / 미적용 시 앱 위·변조 탐지 등 상응 보안 구현 (APK 해시 서버 검증 흐름)
- [ ] FV-9: 서비스 특화 취약점, 난독화 도구 적용(`minifyEnabled true` 등)

**[결과 처리]**
- [ ] 취약점 발견 시: 보완요청서 작성(검증기준 항목 / 보완요청 내용 / 결과 캡처) — 예: `FV-4. 중요정보 관리 | 비밀번호를 평문으로 전송함` (p.44~45)
- [ ] 보완조치 확인: 보완조치내역서의 조치사항·수정 소스 경로 확인 — 예: `보안서버(SSL 서버) 구축을 통해 비밀번호 암호화 전송 * src/ssl.java` (p.46~47)
- [ ] 결과보고서 작성: 개요 / 제품 구조 / 검증결과 요약·특이사항 / [부록] 보완내역 (p.48~49)

## 6. 주의사항 / 문서 미기재 항목

**이 가이드라인의 범위가 아닌 것** — 아래 항목은 흔히 모바일 앱 진단에서 기대되지만 **원문에 없다**. 이 가이드라인을 근거로 지적하지 말 것 (p.51 전 범위 확인 기준):

| 항목 | 상태 | 미기재의 성격[^nature] |
|---|---|---|
| 화면 캡처 방지 / 키보드 보안(보안키패드) | **원문 미기재** | 성격 불명 |
| 디버깅 탐지(anti-debugging) / debuggable 플래그 점검 | **원문 미기재** (난독화·역공학 방지는 기재됨) | 성격 불명 |
| SSL Pinning / 서버 인증서 유효성 검증 | **원문 미기재** (TLS/E2E 암호화 "권고" 수준만 기술) | 인증서 유효성 검증은 **타 문서 소관** — 진단가이드 2021 기준 28 「부적절한 인증서 유효성 검증」(→ `secure-coding-kr`). Pinning은 **현행 점검 권장** (출처: OWASP MASVS — 구속력 없음) |
| 에뮬레이터·후킹 탐지, 메모리 보호, 접근성 서비스 악용 | **원문 미기재** | 성격 불명 |
| iOS URL Scheme / Universal Link 처리 | **원문 미기재** (Intent 항목은 Android 기준만) | 성격 불명 |
| 진단 도구(정적분석 도구 등) 지정 | **원문 미기재** (언급된 도구는 ProGuard, apktool, `MessageDigest`뿐) | 성격 불명 (도구 선택은 전문기관 재량으로 보이나 원문 근거 없음) |
| 적합/부적합 등급·배점 등 판정 체계 | **원문 미기재** ("요구수준 만족 여부"로만 규정) | **의도적 제외** — 원문이 등급·배점 대신 "요구수준 만족 여부" 방식을 명시적으로 채택 |

기타 주의:
- 검증 대상 한정에 유의 — 모바일 웹/반응형 웹, 단순 컨텐츠 변경은 신청 대상이 아니다 (p.11).
- 세부 항목의 (Android) / (공통) 구분을 지켜라 — FV-2.3~2.5는 Android 전용이다 (p.35).

[^pw]: 비밀번호 자릿수는 원문 내 불일치가 있다: 본문 p.26 "8자리 이상" vs 별표 제2호 FV-4.7 p.35 "9자리 이상". 진단 시 이 불일치를 그대로 인지하고 보고서에 근거 페이지를 병기할 것.

[^nature]: '원문 미기재'의 성격 구분 — `의도적 제외`(원문이 다른 방식을 명시적으로 채택) / `당시 미존재`(발행 시점에 관행 미정착) / `타 문서 소관`(다른 기준 문서가 담당) / `현행 점검 권장`(구속력 없는 현행 모범사례 — 출처 명시) / `성격 불명`(분류 근거 부족 — 무리하게 단정하지 않음). **미기재 ≠ 부적합** — 이 가이드라인을 근거로 지적할 수 없다는 뜻일 뿐, 문서의 침묵이 자동으로 현행 점검 대상·부적합 사유가 되는 것은 아니다.
